# M3 每日自动预测与验收点查询修复设计

## 1. 背景与目标

生产环境的 M3 滚动预测仍按十五分钟运行，但正式验收回填在读取
`energy_forecast_points` 时使用 `batch.station_id`、
`batch.acceptance_run_id` 和 `batch.write_state` 关联过滤。当前 NocoBase
对这些关联过滤返回 HTTP 500，错误为 `sink_http_failed`。调度器又把滚动预测、
验收回填和自定义预测评价串行放在同一个 `forecast` 任务体中，因此验收回填失败后，
自定义预测评价不会继续执行，界面会停留在旧结果。

本次交付同时完成两个目标：

1. 移除验收点查询中的 NocoBase 关联过滤，恢复正式验收基线、实绩回填和评价。
2. 将用户手工成功执行过的自定义预测配置变成每日自动任务，使用户成功执行一次后，
   后续无需再次点击“预测”。

本设计不修改任何历史任务、历史预测点或历史评价结果，也不新增自动任务配置表。

## 2. 已确认的产品规则

### 2.1 每日自动预测

- 调度时间使用 `Asia/Shanghai`，每日从 00:17 开始处理。
- 自动任务按“电站 + 时间颗粒度”独立发现。一个电站成功运行过多个颗粒度时，
  每个颗粒度每天各创建一条新任务。
- 每个颗粒度只选取 `completed_at` 最新的已完成任务。可作为模板的状态仅为
  `succeeded` 或 `evaluated`；排队、运行中和失败任务不得成为模板。
- 自动任务完整沿用模板的预测时长、时间颗粒度和历史数据天数。当前请求合同中的
  模型策略和预期点数继续由这些参数派生，不单独复制可变内部字段。
- 只滚动日期窗口：`history_end` 和 `forecast_start` 设为当天上海时间 00:00，
  `history_start` 按模板的历史天数向前移动，`forecast_days` 和
  `interval_seconds` 保持模板值。
- 自动任务调用与界面手工预测相同的 `CustomForecastService.submit()` 路径，产生新的
  任务和预测点。模板任务以及其他历史任务保持不变。
- 自动任务成功后也属于已完成任务。若用户后来手工成功执行同颗粒度的新配置，
  新任务因 `completed_at` 更新而从次日开始自动成为模板。
- 某电站某颗粒度从未成功完成任务时，系统不为它猜测默认配置，也不创建自动任务。
- 模板不设失效期。只要某颗粒度至少成功完成过一次，后续每日持续自动预测，
  直到将来另行实现显式停用能力；显式停用不在本次范围内。

### 2.2 历史任务生命周期

- 已完成但预测目标时间尚未全部过去的任务继续回填实际值。
- 满足评价条件后，任务由现有评价服务转为 `evaluated`，并参与近七日统计。
- 已评价任务保持只读，用于历史查询、效果对比和问题追溯。
- 失败任务保留用于排查，但不成为自动任务模板。
- 不自动删除、覆盖、重跑或归档历史任务。

## 3. 总体架构

新增独立的 `DailyCustomForecastService`。该服务只负责：发现模板、构造当天请求、
检查当天自动任务状态、提交缺失任务和控制有限重试。它依赖
`CustomForecastRepository` 和现有 `CustomForecastService`，不直接训练模型、读取源数据
或写预测点。

`CustomForecastRepository` 新增固定查询边界：

- 对现有六种允许颗粒度逐一查询该电站的 `succeeded` 和 `evaluated` 任务，按
  `completed_at`、`createdAt` 倒序，每种颗粒度只严格解析最新一条作为模板。
- 按电站、当天 `forecast_start` 和 `requested_by=m3_daily_scheduler` 查询当天自动任务，
  用于幂等和重试判断。

不使用 NocoBase `distinct`、分组、全量历史扫描或关联过滤。每站每次检查最多执行六次
模板查询；当天自动任务最多为六种颗粒度各三次尝试，查询规模固定有界。

自动任务仍由专用的单工作线程执行器运行，不占用调度器线程。现有
`max_pending=16` 可以容纳两个电站、六种颗粒度共十二条每日任务；容量暂时耗尽时，
后续调度扫描会重新调度仍为 `queued` 的同一任务，不创建重复记录。

## 4. 每日自动任务数据流

### 4.1 正常流程

每个滚动调度时刻 `02/17/32/47` 都允许调用每日自动任务检查，但 00:17 之前立即跳过。
服务对已经完成当日全部颗粒度的电站在内存中记忆成功日期，避免整日重复查询；
Worker 重启后内存状态清空，通过持久化任务重新判断，因此也能补建当天任务。

对一个电站的处理顺序为：

1. 对每个允许的时间颗粒度读取并严格验证该站最新可用的已完成任务。
2. 丢弃没有成功模板的颗粒度，保留每个其余颗粒度的唯一最新模板。
3. 读取当天由 `m3_daily_scheduler` 创建的任务。
4. 对每个模板构造当天 `CustomForecastRequest`。
5. 若当天该颗粒度已有 `queued`、`running`、`succeeded` 或 `evaluated` 任务，
   不再创建另一条正常任务；排队和运行中的任务由后续扫描继续观察。
6. 若不存在任务，使用确定性幂等键调用现有 `submit()`。
7. 所有颗粒度均进入成功终态后，缓存该站当天已完成；未完成时在下一个滚动时刻复查。

自动任务的 `requested_by` 固定为 `m3_daily_scheduler`，不得与 API 手工任务的
`m3_operations_api` 混用。

### 4.2 幂等键

幂等键由以下稳定值构成并限制在现有 128 字符合同内：

- 上海日期；
- 电站 ID 的短哈希；
- 时间颗粒度；
- 模板配置的稳定摘要；
- 重试序号。

同一次扫描、Worker 重启和 HTTP 不确定提交都会命中同一条任务。配置摘要覆盖历史天数、
预测天数和颗粒度，防止一个键被不同请求复用。

### 4.3 失败与有限重试

- `submit()` 在持久化后因执行器容量不足而失败时，任务仍为 `queued`；下一次扫描用
  同一幂等键重新调度。
- 自动任务进入 `failed` 时保留原记录。系统为同一电站、日期和颗粒度最多创建三次
  自动尝试，每次使用递增重试序号和新的任务记录，不修改失败任务。
- 三次均失败后停止当日重试并发出 `daily_custom_forecast` 告警，避免无限任务风暴。
- 次日仍从最近一次成功完成的模板重新开始，不要求用户再次点击。
- 一个颗粒度失败不得阻断同站其他颗粒度，也不得阻断另一电站。

## 5. 验收点查询修复

### 5.1 直接批次查询

`AcceptanceService` 不再对 `energy_forecast_points` 使用任何 `batch.*` 过滤。它先查询
`energy_forecast_batches`，过滤条件全部为批次表直接字段：

- `station_id`
- `acceptance_run_id`
- `write_state=complete`

查询只读取批次主键、身份、签发时间、基线窗口和写入状态，并按现有索引字段
`issued_at` 排序。Worker 严格验证：

- 批次属于目标电站和验收任务；
- 主键为正整数且不重复；
- 状态为 `complete`；
- 每个批次覆盖一个合法的 24 小时正式窗口；
- 批次位于活动七日窗口内且日期不重复。

### 5.2 按 `batch_id` 查询点

对每个严格验证后的完整批次，Worker 使用点表直接字段查询：

- `batch_id=<批次主键>`
- `unique_id=<序列>`
- 必要的 `data_time` 范围

批次数最多七个，因此采用逐批次直接等值查询，不依赖 `$in` 或 NocoBase 关联展开。
Worker 合并结果后继续执行现有的主键、时间拓扑、物理范围、重复点和精确点数验证。
回填和七日评价共享同一个“完整批次身份解析”边界，避免两套过滤规则再次漂移。

相应更新 NocoBase 集合合同和 Worker 最小权限：

- 批次 `list` 允许上述直接过滤字段和固定读取字段。
- 点 `list` 允许 `batch_id`、`unique_id`、`data_time` 直接过滤。
- 删除 Worker 对 `batch.station_id`、`batch.acceptance_run_id`、
  `batch.write_state` 关联过滤的依赖和合同声明。

### 5.3 正式基线不受回填阻塞

`run_baseline()` 只负责在精确 01:02 生成并持久化当天正式基线，再同步验收进度；
不再在写基线之前调用历史实绩回填。历史实绩由滚动任务中的独立
`acceptance_backfill` 阶段处理。这样即使实绩源或旧点查询暂时失败，也不会丢失当天
不可补造的正式基线。

## 6. 调度阶段隔离

当前 `forecast` 任务体改为阶段化执行，每个阶段独立捕获异常、记录准确任务名并继续：

1. `forecast`：生成十五分钟滚动预测。
2. `acceptance_backfill`：在验收开关开启时回填正式验收实绩。
3. `custom_evaluation`：补算所有达到评价条件的自定义预测任务。
4. `daily_custom_forecast`：00:17 后检查并提交每日自动预测。

一个阶段失败不阻断后续阶段、其他颗粒度或其他电站。告警继续使用稳定错误码，
但 `task` 改为实际失败阶段，避免所有问题都显示为 `forecast`。

每日 01:02 的 `acceptance_baseline` 保持独立槽位。`M3_ACCEPTANCE_ENABLED=false` 时仅跳过
正式验收基线和回填，不得跳过滚动预测、自定义评价或每日自动任务。

Worker 启动恢复顺序为：

1. 恢复现有滚动模型状态。
2. 验收开关开启时恢复验收写入和摘要。
3. 恢复 `queued/running` 自定义任务。
4. 若上海时间已到 00:17，执行当天自动任务补建检查。

各步骤继续按站隔离告警。每日自动任务补建失败会影响该步骤的健康状态并告警，但不会
撤销已经恢复的其他资源。

## 7. 状态与界面语义

- 每次自动执行产生普通的自定义预测任务，使用现有查询和结果接口，不新增 Dashboard
  JSON 字段。
- 同一电站、颗粒度和预测时长的“最新结果”查询自然返回最新成功的自动任务。
- 近七日统计继续由所有满足条件的已完成任务和实绩评价构成，不删除旧任务。
- 当天自动任务仍在排队或运行时，界面沿用现有状态展示；成功后切换到新结果。
- 失败的自动尝试保留在任务历史中用于诊断，但不会覆盖最后一个成功结果。

## 8. 错误处理与告警

新增或明确使用以下任务名和错误边界：

- `daily_custom_forecast`：模板查询、当天任务查询、提交或重试失败。
- `acceptance_backfill`：正式点列表、实绩读取或点更新失败。
- `custom_evaluation`：自定义任务实绩回填或评价失败。
- `acceptance_baseline`：精确基线生成、发布或进度同步失败。
- `forecast`：滚动预测自身失败。

保留底层 `sink_http_failed`、`job_capacity_exceeded`、`idempotency_conflict` 等现有错误码。
合同错误不得静默降级；合法的“尚无成功模板”是正常空状态，不告警。

## 9. 代码范围

预计修改：

- `m3_worker/services/daily_custom_forecast_service.py`：新增每日模板发现、补建和有限重试。
- `m3_worker/services/custom_forecast_repository.py`：新增最新已完成模板和当天自动任务查询。
- `m3_worker/scheduler/runner.py`：每日检查槽位、阶段隔离和准确告警。
- `m3_worker/services/acceptance_service.py`：先查批次、再按 `batch_id` 查点，并移除基线前回填。
- `m3_worker/main.py`：装配每日服务并加入启动补建。
- `m3/contracts/nocobase_collections.json`：把验收点读取权限改为直接字段过滤。
- 对应的 scheduler、custom service/repository、acceptance 和 collection contract 测试。

明确不修改：

- 历史任务、历史预测点和历史评价记录。
- 自定义预测 API 请求与响应合同。
- StatsForecast 模型实现和选型算法。
- Dashboard 页面布局、M1、M2、M4 或 Node-RED 业务 Flow。
- 新增自动任务配置表或管理界面。

## 10. 测试与验收

实现采用测试驱动，至少覆盖：

1. 同一电站多个时间颗粒度每天各提交一次。
2. 每个颗粒度只复制最新完成任务的历史天数、预测天数和颗粒度。
3. 失败、排队和运行中任务不能成为模板。
4. 用户手工完成新配置后，次日自动采用新配置。
5. 00:17 前不创建；00:17 后启动或重启能补建。
6. 重复 tick、重启和不确定 HTTP 提交不产生重复正常任务。
7. 排队任务可重新调度；失败任务最多产生三次独立尝试。
8. 一个颗粒度失败不阻断其他颗粒度和其他电站。
9. 验收回填和评价只按批次直接字段及点 `batch_id` 查询，测试明确禁止 `batch.*`。
10. 首日无历史批次时，01:02 正式基线仍能发布。
11. 验收回填失败后，自定义评价和每日自动任务仍继续执行。
12. 验收开关关闭时，仅验收阶段被跳过。
13. 现有自定义预测、近七日评价、滚动预测和 NocoBase 合同测试无回归。

上线验收观察：

- 00:17 后每个已有成功模板的“电站 + 颗粒度”出现一条新任务。
- 新任务配置与该颗粒度上一条最新完成任务一致，仅日期窗口滚动。
- 日内重复扫描不产生重复正常任务。
- Worker 日志不再出现由 `batch.*` 查询导致的 `sink_http_failed`。
- 人为使验收回填失败时，日志显示 `task=acceptance_backfill`，随后
  `custom_evaluation` 和每日任务仍可完成。
- 自定义任务达到评价条件后自动从 `succeeded` 进入 `evaluated`，近七日统计出现数据。

## 11. 上线与旧验收任务处理

当前 `acceptance-20260829-station1` 和 `acceptance-20260829-station2` 在故障期间没有成功
写入首日开始的完整正式基线点，不能在事后补造为合规的七日验收证据。部署顺序为：

1. 保持 `M3_ACCEPTANCE_ENABLED=false` 部署并验证每日自动任务、滚动预测和自定义评价。
2. 更新 NocoBase Worker 角色，使批次和点表支持本设计的直接字段固定查询。
3. 使用生产 Worker Key 对批次直接过滤和点 `batch_id` 直接过滤执行只读探测。
4. 将旧的不完整验收任务标记为取消，保留已有记录用于审计，不删除数据。
5. 创建从未来一个上海时间 01:00 开始的新七日验收任务。
6. 重新启用 `M3_ACCEPTANCE_ENABLED=true` 并重建 Worker。
7. 次日 01:02 验证两站各写入一个 `complete` 批次及每序列 96 个点；随后观察
   `acceptance_backfill` 不再报关联过滤 500。

只有新窗口连续七天的正式基线和实绩可以作为新的完整验收结果。旧自定义预测任务与该
正式验收任务是不同数据域；旧自定义任务继续按第 2.2 节自动评价和保留。
