## updateOrCreate 响应兼容（2026-09-18，本地待部署）

现场ES01报事件表 `updateOrCreate` HTTP200、`invalid_response`。核对NocoBase官方复合操作实现及项目M3既有解析器，发现M2仅接受记录对象，未兼容更新分支的单条记录数组。现统一接受 `data: {...}` 与 `data: [{...}]`；空数组、多条数组、非记录元素及错误响应继续拒绝，诊断采用相同判定。该修复不将HTTP200直接当作保存成功，不清空队列，不自动补算历史。

68项存储、补偿队列、分钟任务、入口、自检及Flow专项通过，覆盖单条数组确认后出队，以及空/多条/畸形响应拒绝。尚未取得该条现场响应正文，因此单条数组是有源码依据的兼容性判断，生产是否消除此错误须更新后核实。只读查库已确认ES02新增事件ID33，创建于北京时间13:35、13:37仍有更新，不能将ES01积压等同全部事件仍停止。最小发布仍仅更新 `m2/station_efficiency_nocobase.py`，沿用现有Flow；观察自动分钟结果的 `saved/failed/outbox_pending` 和事件表回读，不手动运行写入探针。

官方依据：https://github.com/nocobase/nocobase/pull/10403/files ，复合操作在更新分支返回 repository.update 的结果；本地既有参考为 `m3/worker/clients/nocobase_api.py` 的 `_parse_upsert_record_envelope`，本轮未改M3。

## 设备历史数值类型修复（2026-09-18，本地待部署）

现场只读自检显示两站规则开启、三个历史查询成功，但事件判定均抛出 `HistoryError`。本地只读复现确认：NocoBase 设备表将 `temperature_c` 等数值字段返回为十进制字符串，温升判定器只接受有限数值，导致整站事件判定中断。`fetch_device_points` 现仅在读取边界转换设备数值字段；保留空值、负温度和带符号电池功率，拒绝布尔值、非数值字符串及非有限值，不放宽判定规则、不改库内数据。

120项相关专项通过。北京时间12:46起的同一批真实七分钟数据，ES01含14个设备点、ES02含42个设备点；转换前均报“temperature_c 必须是有限数值”，转换后均判定成功，ES01无待更新事件、ES02产生1条待更新事件。纯计算回放未执行任何事件写入。

最小修复发布只需备份后更新 `/userdata/holo/pyfiles/m2/station_efficiency_nocobase.py`，再运行下方只读自检，确认 `evaluation_only.status=ok`。本轮生产反馈的 outbox 积压分别为ES01两条、ES02三十条；写入失败根因仍未确认，不能以判定通过宣称整个事件链路恢复。真实写入需由既有任务观察诊断及回读，历史缺失不会自动补齐；不清队列，不因该类型修复改变超时、阈值或效率超过100%的处理规则。

## 分钟瓶颈存储诊断（2026-09-18，本地待部署）

当分钟任务返回 `partial`，且警告为 `bottleneck_event_save` 或 `bottleneck_history` 时，分钟主表成功不代表事件链路成功。新增的存储诊断在失败时立即向 stderr 输出一行 JSON，仅包含表、操作、错误类型、HTTP 状态和耗时；不输出请求地址、Token、请求/响应正文或异常原文。成功请求不输出诊断。该改动不修复尚未确定的生产根因，不改变重试、规则、队列或超时。

最小安装步骤：

1. 在服务器备份 `/userdata/holo/pyfiles/m2/station_efficiency_nocobase.py`，再用仓库同名文件更新它。无需替换入口脚本或本机凭据配置，保留原 outbox 路径及数据库。
2. 修改 Node-RED 原「丢弃分钟stderr」Function 节点（ID `d55c1e0a8d4f9013`）：将仓库 Flow 中同 ID 节点的 `func` 粘贴进去，改名「解析分钟存储诊断」，输出接到现有「分钟写入错误」Debug。输入仍接分钟 exec 的第二路输出。
3. 仅部署修改过的节点，等待下一轮既有自动采集；不手动执行 `minute` 或启用清理。整组 Flow 已同步，但无需为了诊断替换整组。
4. 查看 `source=m2_store_diagnostic` 的 `diagnostics` 数组。`collection` 指出失败表，`operation` 指出 `list` 或 `updateOrCreate`；`http_error` 携带 HTTP 状态码，`timeout` 和 `network_error` 区分超时及其他连接错误，`invalid_json`、`response_error`、`invalid_response` 表示响应异常。没有 HTTP 响应时状态为 `null`。

诊断修订：现在按操作区分响应结构，`updateOrCreate` 返回空数组、多条数组或非记录内容时输出 `invalid_response`，兼容单条记录数组；`destroy` 正常返回整数时保持静默。不把响应格式错误自动当作写入未发生，也不自动增加重试。

无法拿到完整 Node-RED 诊断时，可将 `m2/scripts/check_bottleneck_health.py` 安装到服务器同样的包内路径，然后在 Node-RED 实际运行的容器/环境执行：

```sh
cd /userdata/holo/pyfiles
python3 m2/scripts/check_bottleneck_health.py
```

该脚本加载既有入口及配置，仅读取三个历史接口、规则及 SQLite outbox；不执行 `minute`、`cleanup`、POST 或补写。outbox 使用 SQLite `mode=ro`，不会经由自动建表的业务队列函数打开；只检查至多20条排队记录的 JSON 和构建保存结构所需标识，不代替服务器字段/写权限校验。`evaluation_only` 是本地纯计算，`written=0`；接口状态和耗时会逐项输出，不输出凭据、完整地址、响应正文或事件内容。终端环境变量应与 Node-RED 一致，否则只代表该终端配置。

回退时恢复备份的 Python 文件，将该 Function 恢复为 `return null;` 并断开其输出即可。不要清空事件补偿队列。此次 58 项存储、分钟任务、入口、只读自检及 Node-RED 离线专项通过；未进行真实写入或生产部署。

## 页面使用

- 效率曲线：选择日期后点击「查询」，或使用「前一天」「后一天」「回到今日」。历史曲线固定展示北京时间 00:00–24:00；分钟缺失或链路未运行时保留断点，不补零。历史日期下显示该日累计效率，仍按有效分钟累计输出/输入计算，不对效率取算术平均。
- 效率瓶颈：「曲线当日」显示与上方曲线同一天的事件；「历史记录」支持日期范围、近7天/近30天、类型与最新状态筛选，每页10条。日期范围含起止两天，单次最多31天，不限制只能查看最近31天。
- 历史记录显示完整开始时间和恢复时间；「查看曲线」打开事件开始当天。若事件早于查询范围开始，打开查询范围第一天。跨日事件保留一个完整生命周期，状态为当前已保存的最新状态，不是历史时刻的状态快照。
- 电站切换重新查询所选日期与日期范围。实时自动刷新不会覆盖已选历史曲线或历史事件；失败、超时与空结果分别提示。
- 历史表在窄屏中可左右滚动，查看完整判定数据、影响链路及曲线入口。

## 只读接口

沿用 `GET /energy-efficiency-api`，默认查询行为保持不变。

| 操作 | 查询参数 | CLI |
|---|---|---|
| 实时看板 | `station_id=ES02` | `dashboard ES02` |
| 单日效率历史 | `operation=history&station_id=ES02&date=2026-09-06` | `history ES02 2026-09-06` |
| 瓶颈历史 | `operation=events&station_id=ES02&start_date=2026-09-01&end_date=2026-09-06` | `events ES02 2026-09-01 2026-09-06` |

- 历史读取直接访问既有 `t_efficiency_points`、`t_efficiency_bottleneck_events`，不读取实时设备源，不触发计算、写入或清理。
- `history` 返回 `operation`、`station_id`、`range`、`summary`、`trend`、`events`。当日最多1440个分钟点；查询今天时仅返回截至查询时间的记录。`range.cutoff_time` 表示事件阴影截止时间，完整历史日到次日00:00。
- `events` 返回 `operation`、`station_id`、`range`、`events`。Node-RED 与 Python 均校验日期、未来日期、顺序和31天范围。前端对所查区间完整事件列表做类型、状态筛选与分页。
- 日期参数为 `YYYY-MM-DD`；数据库读取使用北京时间自然日转绝对时间的区间 `[start, next_day_after_end)`。事件按 `start_time < range_end` 且「活动中，或已恢复且 `end_time >= range_start`」查询，包含在查询范围之后才恢复的跨日事件。
- Node-RED 对 HTTP 操作做只读白名单校验，`minute`、`cleanup` 不通过该 HTTP 查询入口开放。
