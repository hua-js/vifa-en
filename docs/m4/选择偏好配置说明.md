# M4 方案选择预览

更新：2026-09-08。数学核心及最终候选决策均使用 Pyomo/HiGHS，先计算 balanced/cost/pv，再按显式偏好复验并数学选择，输出中文解释和比较记录，不需要 AI 调用。原确定性程序保留为独立审计基线。仅生成预览，EMS 未下发；电站 1 偏好保持原值，电站 2 尚未配置。新入口见[求解器决策说明](求解器决策说明.md)。

## 页面操作

按[调度参数配置说明](调度参数配置说明.md)启动本地服务并打开 `/m4`，选择单个电站：

1. 核对调度参数和当前输入，启动候选计算。
2. 在“方案选择”中打开“选择偏好”，明确填写运营偏好、需量容差和完整候选顺序后保存；指标模式另填指标容差。无默认值；两个电站分别配置。
3. 点击选择按钮。服务复核当前输入及候选，页面展示选中方案、中文理由、偏好版本、计划引用和三层比较记录。
4. 手动切换候选只改变曲线预览。清除偏好后回到待配置，刷新页面后需要重新发起选择。

| 配置 | 含义 |
|---|---|
| 运营偏好 | 按候选顺序，或按净电费、推荐 SOC 累计偏离、未吸收光伏指标选择 |
| 需量峰值容差 | kW；第一层最小峰值超限附近允许保留的差值 |
| 需量累计容差 | kWh；第二层最小累计超限附近允许保留的差值 |
| 偏好指标容差 | 指标模式分别为元、百分点·小时或 kWh；按候选顺序时隐藏并固定为 0 |
| 候选顺序 | balanced/cost/pv 各一次；顺序模式在需量两层筛选后直接使用，指标模式在指标并列时使用 |

容差必须是非负有限数，不改变计划安全校验。保存偏好不重算候选，也不修改调度参数。并发保存冲突时保留当前草稿，需主动重新读取最新偏好再修改。

## 电站 1 已确认的业务规则

电站 1 无光伏：先最小化需量峰值超限，再最小化累计超限，然后优先 balanced 均衡方案，其次 cost 节费方案。balanced 指方案名称，不比较推荐 SOC 指标。真实联调发现浮点微差后，两项需量比较容差设为 1e-6（kW / kWh），只消除数值微差；仍先筛选需量。

对应配置：`metric=profile_priority`，`tie_order=[balanced,cost,pv]`，`metric_tolerance=0`。保留现有三候选契约，pv 排最后，不使用光伏指标；它仍是零光伏输入下求解的数学候选。若 balanced/cost 被需量层淘汰或复验失败，可能只剩 pv 可选，不为保留候选名称而放宽需量或安全规则。

## 接口与持久化

- `GET /m4-api/stations/{station_id}/selection-policy`：返回本站 revision、version 和 policy；初始 revision=0、policy=null。
- `PUT /m4-api/stations/{station_id}/selection-policy`：保存显式偏好或清除，必须提供读取时的 expected_revision。服务器生成偏好标识和版本。
- `POST /m4-api/stations/{station_id}/selection`：只接受 candidate_run_id、policy_revision；计划与指标从服务器当前候选取出，不接受浏览器提交的计划。

保存请求结构如下，实际值由运营口径确定：

```text
{
  "expected_revision": <当前 revision>,
  "preferences": {
    "metric": <profile_priority | energy_cost | preferred_soc_deviation | pv_unabsorbed_energy_kwh>,
    "demand_peak_tolerance_kw": <非负有限数>,
    "demand_energy_tolerance_kwh": <非负有限数>,
    "metric_tolerance": <非负有限数>,
    "tie_order": <三个候选 ID 的完整顺序>
  }
}
```

清除时 preferences=null，仍需 expected_revision，且 revision 继续增加。偏好存于现有 SQLite 文件的独立 `m4_selection_policies` 表；不重写 settings 表。参数/偏好/候选冲突返回 409，结构错误（含 profile_priority 的非零排名容差）422，上游读取失败 502，存储或服务失败 503。

返回独立 `m4-live-selection-v1`，包含配置版本、候选轮次、偏好 revision、检查时间、原候选有效期及选择审计。新 B1 契约为 `m4-orchestration-v2` / `pending_selection/not_dispatched`，独立选择结果不回写它；旧 v1 编排文件不再接受。

## 时效和边界

选择前后均检查当前候选、配置/偏好版本、有效期，并重新读取、校验预测、电价、控制与逐柜状态/SOC/能力。只有采样时间或能力来源版本更新而决策内容一致时允许继续使用原候选；有效期不会延长。

页面可见时每 10 秒复核偏好和已选/选择中的服务器候选。发现新轮候选、参数变化、过期或读取失败即清除旧选中标记；晚到响应不能恢复已失效选择。跨窗口变化存在一个轮询间隔及请求耗时的观察延迟。定时复核不重复拉取完整上游数据，选择时的现场检查是快照保证，不是连续现场监控。

自动回归使用临时 SQLite、Mock 上游和真实本地求解器。通过后已重启本地 8844 服务，并按用户确认保存电站 1 偏好（当前 revision=2，需量数值容差已调整），读回一致；原调度参数和电站 2 偏好未改变。未向真实设备下发或部署生产服务。核心 CLI 支持历史回放，不检查当前墙钟；实时门禁由 `m4.settings.selection.LiveSelectionService` 负责。
