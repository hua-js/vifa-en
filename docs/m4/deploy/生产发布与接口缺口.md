# M4 生产发布与接口缺口

更新：2026-09-12。依据当前仓库源码；未登录服务器、未核验线上当前配置。本文是当前版本发布入口，旧接口盘点中的历史样本不代表现在仍然缺数据。

## 本次能够上线的范围

可以交付自动优化计划与看板。后端默认每15分钟自动生成全天优化比较，前端展示参考功率和预计费用。**不能作为自动执行闭环验收：没有 EMS 下发接口和执行回读，执行状态及策略执行日志仍是模拟。**

当前计划从当天零点 SOC 开始计算，不是从当前 SOC 开始的剩余时段滚动计划。白天重新生成的全天计划不能直接整表交给 EMS 执行；接入控制前必须实现当前状态起算、未来时段生效与旧计划替换。

| 电价 | t_peak_diy、t_rate | 需确认生产生效电价与时段。全天输入售电价当前固定0，若要计算上网收益，须提供实际售电价及生效日期 |
| 原 EMS 基线计划 | t_model 时段及功率配置，t_es容量来源 | 是配置而非执行记录；要核对现场当前版本、空档行为、生效日期与站级功率口径 |

| 储能能力/保护 | 配置容量、功率限制、SOC边界及已有状态输入 | 缺 EMS 实时站级可充/可放功率、充放许可、故障降额、控制模式和接管状态；额定/配置值不等于动态能力 |

| 费用与节省 | 同输入下EMS与优化方案的模拟比较 | 是预计节省；实际节省需购/售电计量、实际充放电量、电价版本与统一比较基线，不能仅凭日志“已执行”认定 |
| 服务与网络 | Docker后端、Node-RED页面/API代理 | 后端和Node-RED需共享网络，M4_BACKEND_URL=http://m4-api:8844；健康检查通过不代表上游输入可用 |

## 电站2光伏口径

用户确认：光伏优先供负载，余电回送电网。前端已按此展示，电站1不展示光伏日志。

源码配置 `parameters.pv_export_priority=true` 对应 `load_first_export_priority`；false对应余电储能优先。生产发布前读取两站settings核对站2实际保存值。**前端日志不会修改这一配置，也不能证明现场已经执行。** 当前未替用户更改生产参数。

验收需要同一时段的光伏交流功率/电量、负载、储能充放电、并网点购电/上网电量和采样质量。光伏直供一般是能流分配结果，不要求存在独立“光伏直供指令”。若没有独立计量，可用完整同时间口径的能量平衡推算，并明确标注推算；不能简单把储能充电全部认作光伏余电。

## 需要提供的最小资料

1. **EMS接收接口**：地址/协议、鉴权方式（凭据走安全配置，不写文档）、一条请求和响应示例；明确只接收动作时段，还是接收站级参考功率及如何动态调整。
2. **EMS回读接口**：一条脱敏JSON，至少含电站、计划/指令ID、执行时段、状态、实际功率、采样时间、失败原因。没有接口可以先给拟定字段。
3. **计量来源**：站2并网点购电/上网功率及电量字段、光伏交流计量字段、正负方向、单位、采样周期。已有表可以直接提供表名及一条样本，不必另建接口。
4. **动态能力与接管规则**：EMS可充/可放上限、SOC边界、可用容量、自动/手动模式；通讯中断、计划超时、设备保护时如何回原EMS计划。
5. **上网结算**：售电价及生效时间；若暂不计收益，明确保持0元计价。

上述资料中的1、2、4及实时滚动计划是自动控制闭环前置条件。只发布计划展示版不必等待全部接口完成，但应保留模拟标识。

## 发布步骤

### 本地准备与构建

本次发布包括HTML、后端、Node-RED代理函数与Compose覆盖文件。先解决或逐项确认发布测试失败项，再提交本次正式改动；不要把无关修改混入发布。

发布脚本要求整个Git工作区干净，会从提交导出代码，不会自动包含未提交HTML。当前用户自行在本地构建并推送：

```bash
cd /Users/hua/Documents/LVK/code/vifa-en
VERSION="m4-release-$(date +%Y%m%d-%H%M%S)-amd64" bash m4/deploy/build-and-push.sh
```

脚本输出配套目录、ZIP及不可变提交镜像标签。使用输出的真实标签，不复用旧镜像标签。

### 服务器更新（由用户执行）

上传配套发布包，合并到 `/userdata/holo/pyfiles/m4`，保留原有 `.env`、凭据、数据卷、PV及MAPE覆盖配置。备份方式沿用《部署手册》，包括参数数据库及完整solver-decisions目录。先暂停自动生成并确认没有运行中任务，再停服务备份。

将 `backend/.env` 的 `M4_IMAGE` 设置为本次脚本输出的完整镜像引用；把仓库最新 `m4/deploy/m4-station-power.override.yaml` 放到backend目录。旧覆盖文件曾写死旧镜像，本次已改为读取M4_IMAGE，避免更新.env后仍运行旧版。

以下Compose文件名须与服务器现有文件一致；若还有其他覆盖文件，保留并按原顺序加入，站级覆盖最后应用：

```bash
cd /userdata/holo/pyfiles/m4/backend
# 用服务器原有完整覆盖列表；此处列出已知PV、MAPE与站级覆盖。
M4_COMPOSE_FILES=(-f compose.yaml -f m4-pv.override.yaml -f m4-m3-mape.override.yaml -f m4-station-power.override.yaml)
docker compose "${M4_COMPOSE_FILES[@]}" config --images
docker compose "${M4_COMPOSE_FILES[@]}" pull m4-api
docker compose "${M4_COMPOSE_FILES[@]}" up -d --no-build m4-api
docker compose "${M4_COMPOSE_FILES[@]}" exec -T m4-api python /opt/m4-runtime/preflight.py
docker compose "${M4_COMPOSE_FILES[@]}" exec -T m4-api python /opt/m4-runtime/healthcheck.py
docker compose "${M4_COMPOSE_FILES[@]}" ps
```

生产 `M4_AUTO_PLAN_ENABLED` 默认开启，若维护时关闭，更新后恢复开启；不要使用local_debug_api或skip-mape。保持单容器单worker。Node-RED使用同包HTML和代理函数，保留现有登录鉴权及正确的内部地址；不能只更新镜像而遗漏Template。

回滚使用同样完整Compose列表，将M4_IMAGE改回旧镜像，必要时切换到兼容备份卷；保留旧卷，禁止down -v。
