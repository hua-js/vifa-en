## 1. 交付目标与当前边界

**下发由用户在 M4 界面发起。** 用户选择电站和可执行计划，点击“下发计划”；M4 后端核验权限、计划版本和实时条件后提交 EMS。EMS 接收站级计划，根据实际设备状态分配各柜功率，并负责设备执行、安全保护和结果回传。M4 界面展示整个下发过程及真实执行反馈。

业务链路：用户选择计划 → M4 界面发起下发 → M4 后端校验并提交 → EMS 校验与柜间分配 → 设备执行 → EMS 回执及实测数据 → M4 后端保存 → M4 界面更新。

自动生成计划与下发是两件独立操作。后台每15分钟重算、页面刷新、切换电站、打开历史记录均不触发下发；自动生成的新版本也不会替换正在执行的计划。替换或取消同样由用户在 M4 界面明确发起。

当前 M4 每 15 分钟可自动生成一次完整自然日的 96 点费用比较计划，采用北京时间零点历史 SOC 起算。输出标记为 `historical_preview_only`、`not_dispatched`。它不是从当前 SOC 起算的剩余日执行计划，不能将当天已过去的时段补发给设备，也不能直接截取未来时段作为已验证执行方案。

当前 M4 界面的“立即重算”只生成计划，不承担下发功能；“下发计划”及真实提交、替换、取消、设备执行回读尚未实现。本次材料确定目标流程，不代表这些功能已经上线。看板执行状态与策略日志含模拟内容，不能作为设备执行凭证。`completed` 只表示计算任务完成，不能作为已执行或一定存在可用优化方案的判断。

## 2. 双方职责与站点映射

| 项目 | M4 / 平台 | EMS |
|---|---|---|
| 下发入口 | 用户在 M4 界面选择计划并发起；后端校验操作权限与指定版本 | 接收 M4 后端提交的站级计划 |
| 优化计划 | 站级方向、功率、时间、版本、输入证据 | 接收、校验并反馈是否可执行 |
| 柜间分配 | 不输出逐柜调度指令 | 根据在线状态、SOC、限额及保护状态分配 |
| 安全约束 | 求解前采用已确认的站级边界 | 实时硬保护优先，必要时拒绝或限功率并说明原因 |
| 状态数据 | 消费 EMS 的实时状态与约束 | 提供实测值、时间戳、质量和能力限额 |
| 计划生命周期 | 明确提交、生效、过期、替换与取消 | 原子切换、幂等处理、持续报告实际状态 |
| 效果评估 | 同条件预计费用比较、事后评估 | 提供实际功率、电量、告警和执行记录 |

| M4 标识 | 现场电站标识 | 当前储能范围 |
|---|---|---|
| `station-1` | `ES01` | `emu11`、`emu12` |
| `station-2` | `ES02` | `emu21`—`emu26` |

`emu27` 为电站 2 光伏计量，不纳入储能分配。现场须确认这些标识对应的控制对象及主机。柜范围用于身份校验，不表示每柜始终可用。

用户已要求将电站 1 的 M4 SOC 上限改为 99%；本文不认定生产已经保存成功。联调时读取当时配置和 EMS 硬限制，不将 99% 视为所有电站或设备的固定上限。

## 3. 当前 M4 可提供的数据

### 3.1 只读接口

路径中的 `{station_id}` 取 `station-1` 或 `station-2`。

| 方法与路径 | 用途 |
|---|---|
| `GET /m4-api/stations/{station_id}/settings` | 参数及配置版本 |
| `GET /m4-api/stations/{station_id}/control-sources` | EMS 时段、需量及相关控制来源 |
| `GET /m4-api/stations/{station_id}/daily-inputs` | 当日输入、零点 SOC、输入检查及基线比较准备 |
| `GET /m4-api/stations/{station_id}/daily-plan` | 最新全天比较任务、选中候选和计划点 |

现有 `POST .../daily-plan` 会启动计算任务，`PUT .../settings` 会修改参数；它们不是 EMS 控制接口，不能放入只读轮询流程。

当前服务的宿主机入口默认绑定 `127.0.0.1:8844`；共享容器网络可使用 `m4-api:8844`。这些是内部地址，外部 EMS 的访问入口、网络范围、TLS、鉴权和超时需另行确认，不能将内部接口直接暴露公网。

### 3.2 日计划字段与读取位置

以下路径以 `GET .../daily-plan` 的响应根对象为起点。

| 字段路径 | 含义及使用限制 |
|---|---|
| `station_id`、`run_id` | 电站与本次计算任务标识 |
| `status` | 任务状态：可能为 `empty`、`running`、`failed`、`completed` |
| `message` | 当前任务说明；不是机器状态码 |
| `selected_candidate` | 选中优化候选，可为 null |
| `selected_candidate.status` | 候选求解状态，通常需为 `optimal` 或 `feasible` 才能进一步评估 |
| `selected_candidate.plan_version` | 候选计划版本 |
| `selected_candidate.plan` | 有序计划点数组 |
| `result.usage`、`result.dispatch_status` | 当前为历史预览、未下发标记 |
| `result.record.input_summary.configuration_version` | 本次求解使用的配置版本 |
| `result.record.input_sha256` | 输入证据摘要 |
| `result.record.plan_start_at`、`result.record.expires_at` | 计划起点及本次结果有效期信息；不等于设备确认的生效期 |
| `result.record.daily_comparison` | 与 EMS 基线的预计费用比较；不直接决定执行授权 |

必须先判断响应状态及嵌套对象是否存在，再读取候选。不得只看到外层 `completed` 就使用计划，也不得把全部候选逐一发送。

### 3.3 现有计划点

| 字段 | 单位 / 取值 | 含义 |
|---|---|---|
| `timestamp` | 带时区时间 | 该 15 分钟时段起点 |
| `mode` | `charge` / `discharge` / `idle` | 储能方向 |
| `target_power_kw` | kW，非负 | 站级储能目标功率；方向由 mode 表示 |
| `expected_soc_pct` | % | 该时段结束时的预测 SOC，不是设备目标设置值 |
| `grid_import_kw`、`grid_export_kw` | kW | 模型计算的购电、上网功率，不是储能控制指令 |
| `pv_unabsorbed_kw` | kW | 模型中的未吸收光伏功率 |
| `demand_exceed_kw` | kW | 模型中的需量偏差 |

示例仅解释单个计划点，不可直接下发：

```json
{
  "timestamp": "2026-09-15T10:00:00+08:00",
  "mode": "discharge",
  "target_power_kw": 120.0,
  "expected_soc_pct": 65.0,
  "grid_import_kw": 300.0,
  "grid_export_kw": 0.0,
  "pv_unabsorbed_kw": 0.0,
  "demand_exceed_kw": 0.0
}
```

表示 10:00（含）至 10:15（不含）的站级放电参考功率 120 kW。若 EMS 使用有符号功率，正负号映射由双方书面确认；禁止自行假定。计量点是储能交流侧还是其他口径，也须现场确认。

## 4. M4 界面发起下发流程及契约（待实现）

### 4.1 用户操作与界面反馈

| 操作 / 状态 | M4 界面行为 | 后端与 EMS 行为 |
|---|---|---|
| 查看计划 | 展示当前电站、具体计划版本、生效时间及站级功率安排 | 只读查询，无控制动作 |
| 准备下发 | 提供可执行计划；过期、计算中、历史预览或缺数据时不可下发 | 以当前状态校验或生成未来生效的执行方案 |
| 点击“下发计划” | 固定本次所选电站和计划版本，展示“下发处理中”，防止重复点击 | 校验权限与版本，建立唯一命令记录，再提交 EMS |
| EMS 接收 | 展示“EMS 已接收”或“EMS 已接受，待生效” | 接收回执与应用回执分开保存 |
| EMS 应用 | 设备侧确认后展示“已生效”；有时段执行回读才展示“执行中” | 回传实际生效版本、时间及状态 |
| 拒绝 / 失败 | 显示实际原因；不展示成功状态 | 保留失败记录及旧计划状态 |
| 超时 / 断网 | 展示“下发结果待确认”，按原命令查询 | 不因网络超时认定失败，不创建新命令盲目重发 |
| 替换计划 | 用户明确选择新版本并发起替换 | 校验当前生效版本，EMS 原子切换并确认 |
| 取消计划 | 用户针对指定电站和生效版本发起取消 | EMS 确认取消及后续控制模式后，界面才显示已取消 |

刷新或关闭页面不会取消已提交命令；再次打开时从后端恢复下发状态。切站后仍按命令归属显示结果，不把电站1的回执更新到电站2。界面只展示必要业务状态，技术原因码和完整报文留在对接日志。

### 4.2 M4 界面 → M4 后端

需要新增下发、查询下发状态、替换和取消接口；现有 `POST .../daily-plan` 保持计算用途，不复用为下发接口。接口具体路径在实现时确定。

| 界面提交信息 | 后端处理要求 |
|---|---|
| `station_id` | 校验登录用户对该电站的控制权限，不能只验证登录有效 |
| `source_run_id`、`plan_version` | 从服务端读取指定计划，不能自动换成点击后新生成的版本 |
| `configuration_version`、`effective_at` | 校验用户所见配置及生效时刻；变化时要求刷新方案 |
| `request_id` | 本次用户操作的幂等标识；重复提交相同内容返回同一命令 |
| `replaces_plan_version`（替换时） | 指明被替换版本，不允许无条件覆盖当前计划 |
| `command_id`（查询或取消时） | 关联原下发记录并核验电站及权限 |

后端从已认证会话取得操作者身份和操作时间，不信任浏览器自报身份。正式功率点从服务端校验过的计划取值，不能直接透传浏览器提供的功率数组。命令记录先持久化，再向 EMS 发送；响应或网络状态不确定时按相同幂等键查询、恢复，不能产生重复执行。

若下发前重新求解改变了用户所见的时间、功率或计划版本，应返回更新后的可执行方案供用户查看并重新发起，不能悄悄换一份计划发送。现有全天历史比较计划须先完成执行适配，不能仅增加按钮后直接下发。

### 4.3 M4 后端 → EMS

M4 后端将用户选定且校验通过的站级执行计划提交 EMS。浏览器不直接访问设备、保存 EMS 控制凭据或负责逐柜下发。具体 HTTP/MQTT/现场协议由 EMS 提供；本节不指定尚不存在的接口 URL。

| 建议字段 | 要求 |
|---|---|
| `schema_version` | 明确执行报文契约版本 |
| `command_id` | 一次提交的唯一标识，也是重试幂等键 |
| `station_id` / `ems_station_id` | M4 与 EMS 双方电站标识 |
| `source_run_id` / `plan_version` | 关联求解证据，区分计划更新 |
| `issued_at`、`effective_at`、`expires_at` | 带时区时间；起止采用左闭右开规则 |
| `replaces_plan_version` | 原子替换的旧版本；旧版本不符时拒绝，避免覆盖人工更新 |
| `initial_state` | 求解采用的当前 SOC、采样时间、可用范围及状态版本 |
| `configuration_version` | 已确认的控制约束版本 |
| `points` | 每点包含起止时间、mode 与非负站级 kW |
| `payload_hash` | 报文摘要；同幂等键不同内容必须拒绝 |

M4 需先补齐：当前状态起算、未来生效时间、剩余时段重新求解及可行性校验。跨过生效时间后不得直接发送旧结果，应重新生成或拒绝；不得以替换时间标签的方式复用过期方案。

SOC 门槛、充放电功率、并网限制及设备保护应使用实时有效配置。模型准入还会检查 M3 评分、预测和输入质量；评分统一改动需要 M3、M4 配套发布，不能只依据页面百分比认定执行可用。

## 5. EMS 必须确认的执行行为

1. **接收与应用分开**：网络成功、业务接收、设备应用分别反馈；HTTP 200 不等于设备已执行。
2. **原子替换**：新计划全部校验通过后切换；失败时不得留下半张新计划或新旧时段混用。
3. **重复与乱序**：重复相同命令不重复执行；相同 ID 不同内容拒绝；旧版本晚到不覆盖新计划。
4. **取消**：明确取消的是指定版本还是本站当前计划；取消成功需设备侧确认，并定义取消后的模式。
5. **过期与断联**：不得无限沿用过期计划。保持旧计划、切本地模板或停止充放电的行为由现场确认，不能由平台擅自假设为“安全”。
6. **本地接管与保护**：人工控制、BMS/PCS 保护优先；EMS 回传接管、限功率或拒绝原因，M4停止把原计划标为正常执行。
7. **柜故障或能力变化**：EMS 负责可用柜分配；若无法达到站级目标，应报告可达功率、实际功率及原因，必要时请求重算。
8. **时间**：确认时钟同步、允许偏差、采样延迟、指令延迟、功率变化速率及控制周期。15分钟优化粒度不等于底层设备控制周期。

## 6. EMS 回执与运行数据（待实现）

EMS 回执先进入 M4 后端，由后端保存并提供给界面轮询或推送展示；页面不凭时间推移生成真实执行状态。

建议回执至少包含：电站标识、`command_id`、`plan_version`、接收时间、应用时间、状态、原因码。建议状态区分 `received`、`accepted`、`rejected`、`applied`、`superseded`、`cancelled`、`expired`、`failed`；各状态能否由设备确认、是否允许回退需双方定义。

| 数据 | 必需说明 |

| 实际充放电量、购售电量 | 累计/区间口径、复位规则及计量周期 |
| 接管与降级事件 | 原因、发生时间、恢复时间、当前控制来源 |

## 10. EMS v2.0 协议草稿适配评估

评估日期：2026-09-14。依据用户提供的《小飞将 EPS ⇄ 龙维新电 EMS 通讯协议规范 v2（重构）》、版本2.0、2026-06-15草稿。本文评估协议描述，不代表接口已经部署、联调通过或设备执行能力已验证。协议中的 EPS 角色与 VIFA/M4 后端或现场适配网关的对应关系，须由双方确认。

### 10.1 结论与能力对照

**部分满足。可作为站级即时控制与遥测基础，尚不能直接满足 M4 界面发起、可追溯且有明确有效期的计划执行闭环。**

| 我们的要求 | 草稿提供的能力 | 评估及缺口 |
|---|---|---|
| M4 提交站级要求，EMS 分配多柜 | 单一逻辑聚合柜；EMS 拆分功率及均衡 | 责任边界符合；两个电站需各自绑定逻辑组、地址或凭据，防止交叉路由 |
| 充电、放电、待机 | B1 `/api/v2/work`；B2 `/api/v2/action` | 基础动作具备；`idle` 应映射 `standing`，不能发送 B1 `power=0` 或用 `stop` 代替 |
| 跟踪计划功率 | B1 `power` 是功率上限，EMS 可降额 | 不等同于 M4 计划目标；需确认在安全允许时的跟踪规则、偏差判定及降额原因 |
| 按时间执行未来计划 | B1 仅有 `command_id`、`mode`、`power` | 没有计划批次、时段、生效时间或截止时间，不能直接提交一份时序计划 |
| 重复请求、乱序和超时恢复 | B1 声明幂等，回显 `command_id` | 缺少去重期限、同 ID 不同内容处理、跨命令排序及状态查询；旧命令晚到可能覆盖新命令 |
| 明确执行状态 | B1/B2 回执只表示受理；A1 推送实际状态和功率 | 能观测运行，但 A1 没有关联已生效命令，不能证明是哪次下发产生的执行结果 |
| 替换、取消、断联和过期 | 有 `standing`，`wait` 保留工作意图 | 未定义版本替换、取消回执及断联策略；过期的 `wait` 意图可能在工况恢复后继续执行 |
| 实时状态、能量及告警 | A1 每秒、A2 每30秒、A3 事件推送 | 基础数据覆盖较好；需补站点绑定、质量/新鲜度、补传或状态对账规则 |
| 运行参数一致性 | B3 全量配置写入，回执表示已落库 | 缺少配置版本与生效确认；SOC 上下限尚未列入，需量软目标与关口硬上限不能混用 |

### 10.2 与现有 M4 的具体适配点

1. **下发由 M4 界面发起，持续调度在后端运行。** 用户批准具体计划后，后端持久保存执行任务；关闭网页不应停止计时或丢失任务。自动重算只生成新建议，不自动覆盖用户已经批准的执行计划。
2. **全天回溯比较不能直接作为实时执行计划。** 现有结果从零点 SOC 开始计算。下发前必须以当前有效状态核对未来时段的可执行性；不能补发已过去的时段，也不能仅截取全天结果就认定可执行。
3. **功率口径须分开保存。** M4 计划目标、发给 EMS 的功率上限、EMS 实际功率分别记录。保护降额允许存在，但不能用“已受理”或“方向一致”证明完成了计划；预计收益也不能当作实绩。
4. **站点身份必须可验证。** 草稿 B1/B2 和 A1 没有站点字段。可增加 `station_id` / `logical_group_id`，也可用独立地址和凭据绑定电站；回调入口须具有同等可靠的绑定，不能靠前端当前选中的电站判断归属。
5. **SOC 99% 是运行上限要求，不是电池校准模式。** B3 的 `is_battery_calibration=true` 会放宽至 0–100%，不能作为设置99%的替代。需要明确可配置的运行 SOC 上下限及其与 EMS/BMS 保护阈值的关系。本文不代表线上99%已生效。
6. **需量目标与物理限制分开。** M4 电站1区分经济需量目标与550 kW物理购电上限；草稿 `demand_threshold` 被定义为关口取电上限，不能直接拿经济目标填入而保持原优化语义不变。

### 10.3 建议采用的接入路径

结合草稿已有 B1/B2，建议优先讨论“**M4 后端持久化调度，EMS 执行带有效期的单时段命令**”：

- M4 界面批准并提交选定计划，后端负责未来时段调度、计划版本、替换、取消和审计。
- 每个时段由后端向 EMS 发送充放电上限或严格待机指令；EMS 负责柜间分配和现场保护。
- EMS 必须支持命令过期、顺序约束、实际生效命令回读和断联处理，不能只靠后端定时发送来保证正确性。
- 后端须支持重启恢复、单一调度所有者及超时对账；这些能力是 M4 待实现工作，并非草稿已有能力。

如果要求现场在 M4 后端断联后仍执行已批准的未来计划，则应增加 **EMS 原生计划接口**：接收带版本、时段和有效期的计划，支持整体校验、原子替换、取消及状态查询。现有三个下行接口没有描述这一能力，不能按已支持处理。

### 10.4 请 EMS 团队优先补充的契约

| 项目 | 最低需要明确的内容 |
|---|---|
| 命令时间和顺序 | `effective_at`、`expires_at` 或等价有效期；站级递增序号/控制权代次；晚到旧命令及过期命令不得覆盖当前指令 |
| 幂等与查询 | 同 ID 同内容返回同一处理结果；同 ID 不同内容拒绝；去重保存期限及重启行为；按命令 ID 查询受理、生效、拒绝和失效状态 |
| 执行关联 | 回读 `active_command_id`、实际生效时间、当前方向/上限、实际功率；可用充放电能力及等待/降额/拒绝原因 |
| 替换与取消 | 新旧命令切换规则；取消是否清除保留的工作意图；`standing` 是否覆盖并解除旧 `wait`；取消完成以 EMS 回执/回读确认 |
| 过期和断联 | 命令到期、M4失联、EMS重启、人工接管后的行为及控制权；具体策略由现场确认，不能无限保持旧意图 |
| 配置及保护 | 运行 SOC 上下限、购电硬上限与经济目标区分；配置版本、读取和实际生效状态；EMS也必须校验非法值，不能只依赖上游拦截 |
| 上行可靠性 | 电站绑定、时间同步、数据失效阈值；告警重试和当前告警对账；累计电量在换表、复位和聚合范围变化时的处理 |

草稿将安全拒绝约定为“不算失败、不告警”，M4 接入时应保留其业务含义：保护动作本身不必当成通信故障，但**拒绝、等待和降额必须可见且有原因，不能显示为执行成功**。HTTP成功、业务受理、实际生效、实测跟踪是不同状态。
