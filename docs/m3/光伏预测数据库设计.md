# 光伏预测数据库设计

本次范围：新增天气数据表、光伏预测批次表、光伏预测结果表。现有实测继续从 `t_es_data` 读取 `es_sn=ES02` 的 `ac_solar_power`，不复制实测表，不修改 M3/M4 预测或调度算法。

天气表同时服务两个用途：按时间回查历史天气；保存以后每次获取的天气预报。同一目标时间的不同预报批次并存，不能用最新预报覆盖过去的预报。

## 交付文件

- `contracts/pv_forecast_schema.sql`：三张表完整 PostgreSQL 目标设计，包括字段说明、唯一索引、外键和 CHECK。
- `contracts/pv_forecast_nocobase_payloads.json`：依次发送到 `POST /api/collections:create` 的三个请求。每个 `collections` 元素单独作为请求体，不把整个文件作为请求体。
- `contracts/pv_forecast_schema.py`：上述两种输出的统一结构来源。
- `deploy/create-pv-forecast-collections.py`：离线生成、API 建表和元数据回读工具。
- `deploy/import-weather-history.py`：ES02 历史天气 CSV 校验、分批导入、断点续传及回读工具。
- `deploy/fetch-open-meteo-weather.py`：统一Forecast API获取当前值与小时预报、保存快照、按批次导入。
- `contracts/weather_history_import_verification.json`：本次历史天气导入与逐字段核对记录。
- `contracts/weather_history_idempotence_verification.json`：重复执行时跳过全部已有记录、新增0行的核验记录。

## 三张表

| 表 | 用途 | 关键标识与查询 |
|---|---|---|
| `energy_weather_points` | 历史天气及天气预报，每小时一行 | 唯一 `(es_sn, source_kind, source_batch_id, weather_time)`；另建站点/类型/天气时间及站点/类型/获取时间索引 |
| `energy_pv_forecast_runs` | 预测批次、模型、输入快照、窗口、状态与评估 | `run_id` 唯一；按站点、用途、状态、信息截止时间查询 |
| `energy_pv_forecast_points` | 每批次每15分钟平均交流光伏功率 | `run_pk` 关联批次；批次/目标时间、批次/步数分别唯一 |

`id` 为自增 bigint；时间使用带时区时间；功率和天气值使用带单位字段名与定点 numeric；可变的来源和模型元数据使用 jsonb。业务字段使用英文下划线命名，`createdAt/updatedAt` 保留 NocoBase 系统字段形式。

## 天气数据的保存与查询

`source_kind` 取值：

- `historical_reanalysis`：现有 Open-Meteo archive CSV。属于历史再分析，不标作站内实测或历史预报。
- `forecast`：后续实际获取的天气预报。

现有 CSV 已完整保存 2,952 行；训练时再按有效光伏历史的交集选择，不删除多余历史天气。当前文件覆盖 2026-05-01 00:00 至 2026-08-31 23:00，时区为 Asia/Shanghai，用户确认请求坐标纬度23、经度113。

字段对应：

| CSV 字段 | 存储字段 | 时间语义 |
|---|---|---|
| 时间 | `weather_time` | 来源的整点时间标签，显式带 `+08:00` 入库 |
| 气温(℃) | `temperature_c` | 整点瞬时值 |
| 相对湿度(%) | `relative_humidity_pct` | 整点瞬时值 |
| 总/低层/中层/高层云量(%) | `cloud_cover_pct`、`cloud_cover_low_pct`、`cloud_cover_mid_pct`、`cloud_cover_high_pct` | 整点瞬时值 |
| 短波辐射(W/㎡) | `ghi_wm2` | 前一小时均值 |
| 直接辐射(W/㎡) | `direct_horizontal_wm2` | 前一小时水平面直射均值；不是 DNI |
| 散射辐射(W/㎡) | `dhi_wm2` | 前一小时均值 |
| 降水量(mm) | `precipitation_mm` | 前一小时累计 |
| 10米风速(km/h) | `wind_speed_kmh` | 整点瞬时值；原单位保留 |

例如天气标签10:00的辐照对应09:00–10:00，而光伏结果的 `target_time=09:00` 对应09:00–09:15。不能把所有天气字段统一平移一小时。当前设计接收小时天气；15分钟为光伏输出间隔。

历史回查使用 `GET /api/energy_weather_points:list`，筛选 `es_sn`、`source_kind`、明确的 `source_batch_id` 和 `weather_time` 范围，按 `weather_time` 升序分页。接口仍需要相应集合的读取权限。

预报获取后使用新的 `source_batch_id` 写入，并保留：

- `fetched_at`：真正获取该响应的时间，未来预报必填。未知的历史CSV原下载时间保持NULL。
- `issued_at`：提供方真实起报/发布时间，拿不到时保持NULL，不用获取时间冒充。
- `source_metadata`：请求参数、已知的模型/网格信息、字段单位、时间语义版本、原文件/响应SHA-256。脚本没有记录的信息标未知，不猜测；不存Token。
- `source_batch_id`：对完整来源文件或响应、站点、来源类型、坐标、时区等身份元数据做规范化SHA-256。重复导入同一快照保持同一标识。修订数据使用新批次，不覆盖旧批次。
- `content_hash`：单行规范化内容SHA-256。相同唯一键但哈希不同视为冲突，不能静默覆盖。

查询“当时可用的预报”时先限定 `source_kind=forecast`、`fetched_at <= as_of`，已知 `issued_at` 也必须不晚于 `as_of`，再选择一个完整覆盖目标窗口的批次。历史再分析不能替代当时可获得的预报。不能按每个目标时间各取最新一条而无意混合不同批次。

天气允许NULL以保留缺失语义；`quality_status` 默认为 `unreviewed`，完成字段与覆盖核验后才标记质量。NULL与夜间真实零辐照不同。

实时与未来天气已使用同一个Forecast API：小时预报保存为 `source_kind=forecast` 的物理行；模型当前值current连同自己的valid_at与interval_seconds保存在同批次 `source_metadata.current_conditions` 中，保持现有表的小时粒度。详见 `实时与预报天气采集.md`。

## 预测批次与结果的写入约定

`run_kind=operational` 为实际预测，`backtest` 为历史回测或同输入回算。每批记录 `as_of`、预测窗口 `[forecast_start, forecast_end)`、15分钟间隔、应有点数、模型配置/版本、训练范围及使用的天气批次。

`source_manifest` 保存实际使用的聚合光伏输入快照或可长期访问的不可变快照引用。仅记录原表时间范围和哈希只能检测变化，不能还原旧输入。模型工件/代码版本、归一化参数和必要随机种子也应记录或引用。

`weather_batch_id` 是天气表的一批多行，不能直接给它建立唯一外键。保持当前三表范围，由写入服务按 `(es_sn, weather_source_kind, weather_batch_id)` 核对实际天气行、批次哈希、覆盖窗口和可用时间。

发布 `status=completed` 前，写入服务必须完成以下核验；当前ES02运行预测入口已实现这些完成门槛，详见 `光伏运行预测说明.md`：

1. 输入属于同一电站，天气类型/批次匹配，实际预测使用真实可获得的预报；训练和实测截止时间不晚于 `as_of`。
2. 点数等于 `expected_points`，步数连续且从1开始；每点 `target_time = forecast_start + (horizon_step-1) × 15分钟`，完整覆盖窗口。
3. 最终 `forecast_kw` 有限且非负；原始值可保留负数。缺失点不补零。
4. 有上下界时成对提供，包含点预测，并记录其生成方式与名义覆盖率；没有区间时上下界和覆盖率都留NULL。
5. 全部结果写入并回读校验后再发布完成状态。读取方只消费核验通过的完整批次；完成后不修改该批输入和预测点。

这类跨表一致性不能由单表 CHECK 或两个唯一索引证明。实绩评价继续读取原实测表，结果表不额外保存另一份可变实测；评估结果与实测版本、窗口、覆盖率、计算时间写入批次的 `evaluation_metrics`。

## API 建表方式与 PostgreSQL 差异

NocoBase 字段配置对应 `bigInt`、`decimal`、`date + timezone:true`、`json + jsonb:true`；请求同时包含中文字段标题和界面类型。创建使用固定源 `https://vifa.hlszh.com`，禁止重定向。

建表工具先读取所有同名集合，只要任何一张已存在就不发送POST。成功创建一张后回读核对名称、字段类型/精度/空值/默认值、主键、关系和索引。异常不自动重试POST，不改现有表，不回滚删除已创建表。若部分创建成功，应先检查实际状态，再决定恢复步骤。

**API回读只能证明元数据，不能证明所有物理PostgreSQL约束。** 完整SQL包含命名CHECK；本项目现有 `collections:create` 方式不发送这些CHECK，也不执行SQL迁移。历史天气导入工具执行本次 CSV 的连续时间、数值范围、精度及内容校验；这些校验不约束其他API写入方，也不代替预测发布服务的跨表校验。因此不能宣称全部SQL检查已在数据库强制生效。

SQL主键使用identity，API的 `autoIncrement` 在目标版本可能落实为sequence/serial；需要物理数据库目录检查才能确认具体实现。`createdAt/updatedAt` 由NocoBase管理，直接执行SQL不具有NocoBase更新时间行为。用户要求通过API建表，本次没有连接PostgreSQL或执行SQL。

离线生成：

```bash
python3 m3/scripts/create-pv-forecast-collections.py --write-artifacts
```

执行前准备一个仅用于此次集合管理、具有 `collections:get/create` 权限的API Key，保存到本机用户指定的私有文件，文件权限为0600。不要把Key写进SQL、JSON、命令参数、Git或聊天。

```bash
PV_NOCOBASE_SCHEMA_API_KEY_FILE=/absolute/path/schema-admin.token \
  python3 m3/scripts/create-pv-forecast-collections.py --execute
```

完成后的只读核验：

```bash
PV_NOCOBASE_SCHEMA_API_KEY_FILE=/absolute/path/schema-admin.token \
  python3 m3/scripts/create-pv-forecast-collections.py --verify-only
```

## 历史天气导入

以下命令在 `vifa/` 目录执行。默认只离线检查 CSV，不读取凭据或访问 API：

```bash
python3 m3/scripts/import-weather-history.py
```

导入凭据需要 `collections:get` 以及 `energy_weather_points:list/create` 权限。通过0600私有文件提供，导入并完成核验后删除临时凭据文件：

```bash
PV_NOCOBASE_IMPORT_API_KEY_FILE=/absolute/path/weather-import.token \
  python3 m3/scripts/import-weather-history.py --execute
```

工具按固定文件批次查询已有记录，逐字段一致才跳过，冲突立即停止；每100行创建一次，所有行写完后分页回读整批并重新计算内容哈希。中断后再次运行会先回读已有记录，仅补写缺失行，不自动重试不确定的POST，不覆盖或删除旧批次。调用方应在完整批次验证成功后再消费数据。

仅回读检查使用 `--verify-only`，不会写数据库；缺少任何预期时间则失败。可用 `--report /absolute/path/report.json` 单独保存核验报告，保留首次导入记录。

CSV的未知原下载时间 `fetched_at` 和发布时间 `issued_at` 均保存NULL；本次入库时间由NocoBase系统字段记录。`quality_status=valid` 仅表示通过已记录的数据格式、连续性和范围检查，不表示站内观测精度已验证。
