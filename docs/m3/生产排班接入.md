## 数据合并

- 常规来源：`https://yun.vifa.cn/api/production/schedule`，按日期查询，使用 `X-Api-Key` 鉴权。按用户要求，密钥内置于服务端源码，使用SecretStr避免配置对象直接显示明文，不进入前端或本文。
- 临时来源：已新增 NocoBase 集合 `production_overtime`（临时加班）。只读取已确认记录，草稿和已取消记录不生效。
- 同一电站、日期的临时加班只将指定时段标记为工作；其余时段保留常规排班。不将半天或晚间加班扩成全天，也不叠加重复工时。
- 取消临时记录后，下次预测恢复使用常规排班；不改写既有预测、历史版本或计划表，不自动重算或下发。
- 常规 API 的 `WORK`、`REST`、`HOLIDAY`、`SHUTDOWN` 是每日分类。它不提供班次起止时间，不能从总计划工时反推具体生产时段。
- 当天和未来的事后加班字段为零不表示没有加班，不将 `overtimeHours`、`overtimeForms` 用作日前加班判断。
- 返回行缺失与休息分开，结合 `scheduleHorizonEnd` 标明排班覆盖边界；不得补零或静默当成休息。接口故障、历史覆盖不足与未来未排班的回退行为在接入时分别记录。
- 失败时除 HTTP 状态外，还检查 JSON 业务 `code`；业务错误不能当作有效空表。

## 合并与模型实现

- `m3/worker/clients/production_schedule.py` 固定HTTPS端点和部门映射，分页读取已确认临时记录，检查业务码、返回日期、覆盖边界、重复行和冲突。请求跨度较长时拆分，单段不超过186天。
- `domain/production_schedule.py` 保存任务内不可变快照；`ContextVar` 隔离站点及并发任务，退出或异常时恢复上下文。同一任务训练和预测复用同一份快照。
- API日状态与本地时段模板分开：`WORK` 使用08–12、14–18、19–21作为工作时段；电站2周六按已确认规则仅上午。其余日状态使用休息类型。临时加班只增加所选时段，午休、班间及夜间保持非工作时段。API不能给出具体班次，不从人数或工时推算班次，也不按人数直接缩放功率；后续如标准班次不同应调整本地模板。
- 缺失的历史日期使用周一至周六工作、周日休息的日状态，再按时段模板匹配，清单记录每个回退日期。预测日期缺失则报错；只有该日期存在已确认“全天”记录时，可由此完整定义当日三个工作时段。半天记录不足以补全未知日期。
- SOC区分“这一天是否工作”与“当前时段是否工作”；半天加班仍使该日成为有生产活动的日期，前一天上下文据此匹配。负荷用同一时段类型选历史样本，休息类型使用历史实测，不强制负荷为零。
- 每日/手动SOC保留既有候选比较；常规SOC在启用生产排班后复用`SOCScheduleDelta`增量逻辑，不再走不感知排班的旧曲线拟合。不伪造该固定策略的选模评分，历史不足时明确失败。
- 生产排班模式标记`production-api-overtime-v1`。常规预测不恢复旧选模清单，启动时使用新输入重新选择；既有历史预测保留。
- 成功任务保留清单：每日/手动写入`source_manifest.production_schedule`，常规写入`model_manifest.production_schedule`，包含实际日状态与人数/工时原值、临时记录ID和审计时间、时段规则、获取时间及内容哈希。历史信息口径标记`current_read_not_as_of_archive`，不能把使用当前回读排班的内部留出评分宣称为当时已知信息下的独立回测。
