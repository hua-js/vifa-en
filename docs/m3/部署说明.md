# M3 AMD64 三域部署说明

完整部署、升级与回退步骤见 [AMD64三域Docker部署手册.md](AMD64三域Docker部署手册.md)。
当前代码使用 AMD64 Docker 双容器、三域 HTTPS、Unix Socket 和 NocoBase 普通 iframe。

## 职责

| 组件 | 地址/接口 | 职责 |
| --- | --- | --- |
| VIFA NocoBase | `https://vifa.hlszh.com` | 原始采样、预测结果与验收控制/汇总数据 |
| EMS NocoBase | `https://ems.lvkpower.com` | 页面和普通 iframe 容器 |
| OPDash Node-RED | `https://opdash.lvkpower.com` | 页面、固定 API 路由和 Socket 代理 |
| M3 Worker | AMD64 Docker | 分电站训练、预测、实际值匹配及评估 |
| M3 Dashboard | AMD64 Docker | 已持久化预测与最近实绩的只读聚合 |

## 数据与页面路径

Worker 通过 `https://vifa.hlszh.com/api/t_es_data:list` 读取两个电站的原始采样，
分别处理总负荷与储能 SOC，不合并电站。常规结果保存到四个结果/明细集合；
`energy_forecast_acceptance_runs` 保存正式七日验收的控制与汇总。

自定义和每日预测使用 `energy_forecast_manual_runs`、`energy_forecast_manual_points`、
`energy_forecast_manual_evaluations` 三个集合，保存任务、预测点和可比评估；
不会写入 `energy_forecast_latest` 或正式七日验收表。字段及权限以
`contracts/nocobase_collections.json` 为准。

```text
EMS 普通 iframe -> https://opdash.lvkpower.com/ett?token={{ ctx.token }}
  看板状态 -> /energy-forecast-api -> dashboard.sock -> Dashboard
  自定义/每日预测结果 -> /energy-forecast-api/custom-* -> worker.sock -> Worker
```

页面刷新只读取结果和对应实际值，不触发训练；手动提交与每日调度负责生成任务。
历史不足或质量不合格时返回真实的数据质量状态，不回退为演示结果。

### 当前负载误差评分

当前自定义/每日预测的负载卡片显示“负载加权 MAPE（夜间容差）”。使用实际质量为 valid、预测与实际均为有限数且实际非零的点。北京时间每天 `[00:00,07:00)` 和 `[21:00,24:00)` 为夜间：权重 0.25，绝对误差小于 10 kW 时贡献记 0，但保留该点的权重和分母；达到 10 kW 时使用完整百分比误差，不减去 10 kW。其余时段权重为 1，正常计算全部百分比误差，不使用 10 kW 容差。适用于两个电站及各输出粒度。

评分为 `sum(weight × error_percent) / sum(weight)`，其中仅夜间且绝对误差小于 10 kW 时 `error_percent = 0`，其他情况为 `abs(forecast-actual)/abs(actual) × 100`。卡片同时显示实测回填数、夜间容差置零点数及未加权、未设容差的标准 MAPE。没有有效非零实际点时显示 `—`。实际为零的点不进入任一 MAPE 分母，但计入实测回填数。原有 30% 验收阈值不自动适用于此评分。

这项调整只影响当前负载卡片的评分展示，不更改预测值、选模、SOC、近七日标准 MAPE、正式验收或已保存的后端指标。上线只替换当前 Template HTML，无需重算任务、更新 Flow JSON 或重建 Worker 镜像。

默认 `M3_AUTH_MODE=query_token`。NocoBase 在 iframe URL 中用 `{{ ctx.token }}` 传入当前用户 Token；
页面读取后清除自身 URL 中的 token 参数，只在内存中保存，并通过 `Authorization: Bearer …` 调用所有预测 API。
Node-RED 向 `M3_AUTH_BASE_URL/api/auth:check` 校验当前用户后才访问 Socket。
Token 失效或直接刷新已清除参数的页面时，需要从 NocoBase 重新打开。
Dashboard 只读 Key 和 Worker 管理令牌仍仅保存在服务端，不进入 iframe URL 或页面源码。
首次入口请求含用户 Token，代理访问日志应隐藏该参数；页面响应设置 no-store 和 no-referrer。

Dashboard Socket 不可用时返回 502，单站历史不足只影响该站。

## 页面维护

`m3/node_red` 仅保留以下文件：

- `m3_production_gateway_template.html`：当前页面源码，直接用于生产 Node-RED Template 节点，保留 `{{{m3DashboardAuthModeJson}}}` 与 `{{{m3NocobaseParentOriginJson}}}` 配置注入。
- `m3_production_gateway_flow.json`：生产网关 Flow，维护路由和服务调用。
- `本地机器.txt`：本地机器备注。

只修改 HTML 时直接编辑 Template HTML，不更新 Flow JSON，也不使用页面同步脚本。
在 macOS 可执行 `pbcopy < m3/node_red/m3_production_gateway_template.html`，粘贴到
`m3_prod_page_template` 节点，再选择 `Deploy Modified Flows`，无需重启 Node-RED。

完整导入 Flow 后，需再用当前 Template HTML 覆盖页面节点；Flow 内嵌的页面不会随 HTML 修改自动更新。

## 默认预测日期

- 默认结果按北京时间当天筛选：`forecast_start <= 当天零点 < forecast_end`，然后选取同电站、粒度、预测天数和模型策略下最近完成的任务。跨天的多日预测只要覆盖今天仍可入选。
- 没有覆盖今天的任务时，latest 接口返回原有 404 `not_found`；页面显示“今天暂无匹配预测结果”，清空曲线和摘要，不恢复历史或未来缓存，不回退到旧看板的拼接曲线。
- 页面跨日后的下一次可见刷新重新选择当天任务；明暗模式与原有每分钟刷新间隔保持不变。
- 手动预测仍可用于历史日期，完成后标明“历史预测”和完整起止时间。覆盖今天的结果标明“覆盖今天”；未来结果有独立日期标签，不作为默认结果展示。
- 历史截止时间是排他的零点。Worker 拒绝 `history_end > 今天零点` 的新请求，返回 422 `request_invalid`；页面历史结束日期（含当天）最晚可选昨天，并在输入越界时禁用提交。
- 不修改预测算法、数据表、采样或已有预测记录，不自动重新计算任务。


日期规则更新需同时部署 Worker 的 `custom_forecast_repository.py`、
`custom_forecast_service.py` 和生产 Template HTML；仅修改 HTML 不能替代后端更新。

## 切站与近七日统计

- 每个电站最多维护六套每日滚动配置，分别对应 30 秒、1 分钟、5 分钟、15 分钟、30 分钟和 1 小时；每套任务同时预测负载与 SOC。每种粒度取最近成功完成的任务作为后续配置，新配置成功前仍以原成功配置为准。这不是数据库最多六条任务的限制：每日任务、手动任务和失败重试记录仍按各自任务 ID 保存。
- 历史表单按北京时间自动增长：保持开始日期，结束日期随“昨天”更新，超过90天后移动开始日期以保留最近90天。可见页面每分钟及从后台恢复时更新，即使当天没有预测任务也照常滚动。各站开始日期单独保存在本机浏览器；首次没有偏好时暂用28天，并由首次加载的当前任务初始化开始日期。切站恢复该站开始日期、预测1天和15分钟粒度；刷新或后续任务不能用旧训练范围回退表单。
- 手动将结束日期选为更早日期时，保留历史查询范围，不自动滚动；改回昨天后恢复自动增长。手动编辑日期不被迟到结果覆盖。表单是下一次提交的训练配置；已保存任务的真实训练区间仍由任务详情展示，不因表单滚动而改变。仅表单自动增长不会创建预测或改变Worker每日任务的训练窗口策略。
- 近七日统计独立按电站、输出粒度、预测天数和当前模型策略查询；相同策略下训练历史从 29 天增加到 37 天时，继续纳入旧任务评估，不再按训练天数拆分；今天没有预测也可以显示已有统计。统计面板明确标注口径，加载失败不阻断预测曲线。
- 15 分钟表示每天 96 个预测点。每日调度在北京时间 00:17 后，根据该电站各粒度最近完成的配置生成当天任务；训练窗口保持原有天数并逐日平移，不会自动从 28 天扩大到 29 天。需要 Worker 调度正常运行，页面刷新或切站不会创建任务。
- 已保存任务保留。预测窗口结束后进行评估，满足有效点覆盖等条件的可比任务进入七日统计；七日面板滚动展示，不代表删除更早记录。旧任务保留原始训练配置和预测值，不修改历史归属或重新计算旧预测。少于 28 天与至少 28 天属于不同模型策略，仍分别统计。

本次切站与历史延续更新需部署 Template HTML 和 Worker 的 `custom_forecast_evaluation_service.py`；不更新 Flow JSON，不迁移或删除数据库记录。

## 连续七日验收生产启用

操作员负责在 `energy_forecast_acceptance_runs` 创建并拥有任务身份、窗口和控制字段；Worker 列出任务行，且只能更新 `completed_days`、`result_state` 和 `calculated_at` 三个汇总字段。Worker 只配置一个专用 `M3_NOCOBASE_API_KEY`；同一个角色合并既有明细写权限、新增批次/评估限定读取和任务汇总更新权限，不另配验收任务 Key。示例而非生产 ID：

```text
station_id:          ES01-FULL-ID-EXAMPLE
acceptance_run_id:   acceptance-20260829-station1
window_start:        2026-08-29T01:00:00+08:00
window_end:          2026-09-05T01:00:00+08:00
control_state:       active
completed_days:      0
result_state:        pending
calculated_at:       留空
```

日期仅为示例：真实任务均从上海时间 01:00 开始，恰好七天后结束，并在首日 01:02 调度槽前创建。

以下探针用同一个 Worker Key 覆盖任务、完整批次、`writing` 恢复批次和评估的固定读取合同。Authorization 头从 stdin 传给 curl，不出现在 curl argv。不得用生产记录测试写入；在 NocoBase 角色 UI 中核验同一 Key 只有：latest `list/updateOrCreate`、batches `list/update/firstOrCreate`、points `list/update/firstOrCreate`、evaluations `list/updateOrCreate`、acceptance runs `list/update`，并逐项核对机器合同中的字段/过滤/排序/写入/记录键。

```bash
read -rsp 'Worker NocoBase token: ' M3_PROBE_TOKEN
echo
read -rp 'Full station ID: ' M3_STATION_ID
read -rp 'Acceptance run ID: ' M3_ACCEPTANCE_RUN_ID
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_acceptance_runs:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"control_state\":\"active\"}" \
  --data-urlencode 'fields=id,station_id,acceptance_run_id,window_start,window_end,control_state,completed_days,result_state,calculated_at' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_batches:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"acceptance_run_id\":\"${M3_ACCEPTANCE_RUN_ID}\",\"write_state\":\"complete\"}" \
  --data-urlencode 'fields=station_id,acceptance_run_id,issued_at,forecast_start_time,forecast_end_time,write_state' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_batches:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"write_state\":\"writing\"}" \
  --data-urlencode 'fields=id,station_id,acceptance_run_id,issued_at,forecast_start_time,forecast_end_time,status,write_state,model_manifest,content_hash,point_templates' \
  --data-urlencode 'sort=issued_at' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_evaluations:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"acceptance_run_id\":\"${M3_ACCEPTANCE_RUN_ID}\"}" \
  --data-urlencode 'fields=station_id,acceptance_run_id,evaluation_key,window_start,window_end,outcome,calculated_at' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
unset M3_PROBE_TOKEN M3_STATION_ID M3_ACCEPTANCE_RUN_ID
```

1. 核验表约束和 Worker 角色权限。
2. 在 `M3_ACCEPTANCE_ENABLED=false` 下部署新镜像。
3. 为每个需要启用的电站创建一个活动任务。
4. 核验每个活动/空电站查询。
5. 在 `/etc/vifa-m3/m3.env` 中设置 `M3_ACCEPTANCE_ENABLED=true`。
6. 在首个 01:02 槽之前只重建 `vifa-m3-worker`。
7. 在 01:02 后检查首个完整 batch 和任务汇总。
8. 在最终实绩回填和评估完成前保持 `control_state=active`。
9. 仅在 Dashboard 显示终态 7/7 结果后将任务标记为 `completed`。

自定义预测需要重新导入 `m3_production_gateway_flow.json`。普通 iframe 默认使用 `query_token` 模式，
通过当前用户 Token 认证；配置服务端 `M3_STATIONS_JSON`，并从 Worker 的 `M3_ADMIN_API_TOKEN` 生成固定文件
`/userdata/holo/pyfiles/vifa-m3/run/.worker-admin.token` 后，页面启用“开始预测”。Node-RED 只从该文件读取
Worker 管理令牌，令牌不得进入 Flow、浏览器、URL或命令行参数。此模式公开提交预测；需要用户级权限时改用
`postmessage` 模式。
