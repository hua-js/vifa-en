# M1、M2 功能实现：Grill / Discovery Notes
Date: 2026-08-23 · Goal: 根据项目文档，从项目负责人视角穷尽 M1（设备能耗实时监测）与 M2（能源转化效率分析）的产品需求、系统设计、数据接入、算法、界面、测试、部署、责任和风险，为实际实现形成可靠输入。

## Summary / key decisions

- 本次交付边界已确认：在 2026-09-30 前，基于第一阶段现有能源系统完成 M1、M2 的 L4 验收。
- 第一阶段范围包括 1#、2#配电站及储能、两组原有光伏、市电及关口计量、厂区总负载和双方确认的用电支路。
- 556kW 新光伏若届时不具备接入条件，则不纳入本次覆盖率分母，后续按第二阶段交付。
- M1 按 5/5 通过、监测覆盖率 100% 执行；M2 按 6/6 通过、分析精度不低于 80%（计算误差不大于 20%）执行。
- 访谈目标已纠偏：不是继续解释或拷打验收文档本身，而是以文档为需求基线，提取实现 M1、M2 所需的全部工程决策。
- 现有 EMS 由用户所称的“nonobase”与 Node-RED 实现，系统已有真实数据并可通过接口访问；当前开发阶段允许先使用模拟数据。
- 可选交付形态包括：由 Node-RED 承载并通过 iframe 嵌入现有 EMS，或从零开发新系统；具体路线尚待确认。
- 技术路线已确认采用混合架构：Node-RED 负责真实接口接入、数据清洗和模拟/真实数据切换；新建独立 M1/M2 Web 应用负责实时监测、告警、效率计算和可视化；最终通过 iframe 嵌入现有 NocoBase EMS。
- M2 所需的关键计量数据已确认可用：光伏逆变器交流侧输出、储能充电输入与放电输出、厂区负载侧总量、市电关口购电与上网数据，均按上一问所列范围理解为可从真实接口取得。
- M2 首版效率采用瞬时功率口径，不以 5 分钟滚动电量作为首版实时效率；滚动/累计电量口径可作为后续增强或验收复核能力。

## Source baseline

- 文档来源：`docs/acceptance/附件1 AI 电价负载预测系统 验收清单_修订版.docx`、`docs/acceptance/附件2_AI 电价负载预测系统分阶段纳管设备及数据点位清单_简化版.docx`。
- M1 共 5 项：光伏发电功率实时采集、储能充放电功率/SOC/温度实时采集、负载用电功率实时采集、采集周期不大于 30 秒、异常检测与自动告警；M1 验收要求 5/5 通过，核心指标 K1 为监测覆盖率 100%。
- M2 共 6 项：光→储、储→用、光→用三条链路实时效率，24 小时效率曲线，效率瓶颈识别，算法计算值与人工核算值误差不大于 20%；M2 验收要求 6/6 通过，核心指标 K2 为分析精度不低于 80%。
- 附件 1 的 4 项核心指标 K1-K4 均为否决项；任一不通过则整体验收不通过。未通过项由乙方在 15 个工作日内整改并重新验收。
- 第一阶段范围是甲方现有能源系统：1#、2#配电站及储能、两组原有光伏、市电及关口计量、厂区总负载和双方确认的用电支路；第一阶段接入后需连续稳定运行 14 个自然日并形成测试报告。
- L4 验收节点要求最迟 2026-09-30 完成全部可实施功能并依附件 1 验收；若 556kW 新光伏工程届时不具备接入条件，则不计入该阶段覆盖率且不影响 L4 验收。
- 第二阶段才纳入 556kW 新光伏，并完成采集、通信、分析、预测、告警、授权控制和优化调度接入；其 14 日测试是付款至 97% 和正式质保期起算条件之一，不推翻已通过的 L4 验收。
- 仓库当前无代码、接口点表、数据字典、协议映射、测试记录或交付计划，仅有上述两份文档。

### Q2 — 访谈目标纠偏
- Asked: 原问题询问 M1、M2 的最终验收拍板人。

### Q3 — 既有系统与数据条件
- Asked: M1、M2 是接入既有 EMS/MES/物联网平台，还是从零开发独立系统？
- Captured: 用户原话：“现有一套EMS，是通过nonobase以及node-red去实现的。已有数据，可交付的系统可以是通过node-red去嵌入iframe，也可以从0开发。通过接口访问真实数据，现可以是模拟数据”。据此确认：已有 EMS；技术载体包含 nonobase 和 Node-RED；已有真实数据且可通过接口访问；当前开发可使用模拟数据；最终交付既可以 iframe 方式集成，也可以从零建设。
- Flags: “nonobase”是否指 NocoBase、现有 EMS 的访问方式与版本 -> 用户/系统管理员；真实数据 API 的协议、鉴权、字段结构、频率与测试环境 -> 接口负责人；最终技术路线 -> 本次访谈确认。

### Q4 — M1/M2 交付架构
- Asked: 是否采用混合架构：Node-RED 负责真实接口接入、数据清洗和模拟数据切换；独立 M1/M2 Web 应用负责实时监测、告警、效率计算和可视化；最终通过 iframe 嵌入现有 NocoBase EMS？
- Captured: 用户原话：“确认”。据此锁定混合架构，不把复杂的 M1/M2 页面和分析逻辑全部堆叠在 Node-RED 中，也不替换现有 EMS 主体。
- Flags: 独立应用的具体技术栈、部署位置、iframe 鉴权方式及 Node-RED 与应用之间的数据契约仍待后续确认。

### Q5 — M2 计量边界与数据可用性
- Asked: 真实接口是否能分别提供光伏逆变器交流侧输出、储能充电输入/放电输出、厂区负载侧总量、市电关口购电/上网等独立且带时间戳的功率或电量点位？
- Captured: 用户原话：“有”。按问题上下文，记录为上述四类计量数据均可用，可支持基于实测数据计算三条效率链路。
- Flags: 各点位的准确名称、单位、采样周期、时间戳时区、数据质量码及是否具备链路分项计量 -> 后续接口样例/点表核对；若“有”仅指部分点位，需用户后续纠正。

### Q6 — M2 效率计算窗口
- Asked: 是否采用 30 秒更新、5 分钟滚动电量效率、15 分钟曲线聚合、全天累计电量用于验收复核的口径？
- Captured: 用户原话：“先使用瞬时功率”。据此，M2 首版直接以同一时刻的链路输入功率和输出功率计算效率；滚动电量、15 分钟聚合和全天累计复核不作为首版实时计算的前置要求。
- Flags: 瞬时功率的时间对齐容差、低功率分母阈值、数据过期判定、异常值处理以及后续是否补充累计电量验收口径 -> 后续设计确认。
