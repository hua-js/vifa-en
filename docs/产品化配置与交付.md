# M1 / M4 项目配置与版本化交付

本文描述现有功能的产品化基础改造，不增加监控功能、不接入 MES/EMS 指令下发，也不是生产部署记录。现有 M3、NocoBase 数据契约仍是依赖；只对接符合这些契约的数据源，不声称已支持任意厂商、异构储能能力或任意预测平台。

## 1. 配置边界

- `shared/project.py`：M1/M4 共用的严格项目配置入口。
- `config/projects/vifa.json`：现有项目的兼容配置，不能直接当作新客户默认参数。
- `config/projects/example.json`：不同站号、设备组合的配置示例；示例地址不是真实数据服务。
- `VIFA_PROJECT_CONFIG`：运行时读取的项目 JSON。未配置时使用仓库内 VIFA 配置；交付环境必须显式挂载自己的配置。
- M1～M4 的整体目标是代码复用、项目配置不同、运行和数据各自独立；当前先完成 M4，其他模块按后续任务逐个推进。
- 一个运行实例对应一个项目，可以复用同版本镜像；不同项目必须使用不同配置、凭据、数据库、历史目录和数据卷。不实现实例内项目切换或共享实例多租户，项目内仍可切换电站。
- 配置在进程内缓存。修改后先暂停自动任务，校验配置，再重启相应服务；不要期望热更新。
- 本轮保留北京时间、15分钟/自然日计划及已有数据口径。只支持明确列出的策略类型，不把修改配置当作新增算法能力。

项目配置包含项目/场站身份、站点标识和上游编码、设备名单、光伏能力、数据源地址及策略选择。配置不包含凭据。站点 ID 是稳定业务标识，不要通过重命名复用旧历史。

### 离线校验

从仓库根运行：

```bash
.venv/bin/python scripts/check_project.py --project config/projects/vifa.json
.venv/bin/python scripts/check_project.py --project config/projects/example.json
```

校验仅加载配置，输出公开站点元数据，不取数、不启动计算、不读取凭据。未知字段、重复身份、非法数据源或不支持的配置应修正，不能通过放宽校验上线。

## 2. 数据接入和策略

M1 的基础拓扑、能量数据和光伏数据源，M4 的 NocoBase 数据源，从项目配置读取。M4 仍使用已明确的表/字段合同；换域名不意味着新实例自动满足字段和权限要求。上游请求继续限定在服务端可信配置地址，不允许浏览器选择目标，不允许跨地址重定向转发凭据。

M4 通过配置选择已有 `cost_first` / `peak_reserve` 策略，不通过站号名称隐式选择业务规则。保留已有策略版本标识以便历史追溯；历史版本字符串中出现旧站名，不表示仍按该站名路由。

物理购电上限、设备名单和项目告警特例属于项目配置。VIFA 的设备特例只用于已确认的当前项目，不应复制到新客户配置。不同容量设备的聚合能力仍受现有算法范围约束，不因此宣称已实现异构柜能力分配。

M4 当前预测读取仍依赖 M3 约定的接口和评分结构。更换上游站号时，必须确认预测服务支持相同站号；M1/M4 的配置可复用不等于本轮已经把 M3 全部产品化。

M3 待办（本轮不修改）：M4 的 `platform_gateway` 传输当前通过内部站点 ID 的连字符转下划线推导 M3 路由别名，尚无独立映射。例如内部 ID 为 `north`、上游编码为 `ES01` 时会请求 `north/latest`，无法直接对接仍使用 `station_1/latest` 的现有网关。后续接入时需明确配置网关站点标识并核对契约；当前不能声称任意新站号已经完成预测联通。

## 3. HTML 与 Node-RED

- M1 页面唯一源：`m1/web/dashboard_energy.html`。
- M4 正式页面唯一源：`m4/web/M4优化调度控制台-线上版.html`。
- M4 Flow 的 Function 源：`m4/deploy/node_red/*.js`；仅首次安装或网关变更时显式`--include-flow`生成完整Flow。纯HTML变动只修改正式源，不同步Flow或额外Template副本。
- M4 新增鉴权后的 `GET /m4-api/project`，供页面加载动态站点列表和配置版本。必须同步更新 Flow 和后端，不能只换 HTML。
- M4 网关验证站号语法，后端项目注册表负责判断是否存在；未知站点不能回退到别的电站。
- M1 的实际 Node-RED Flow 尚未提供。联合包提供程序与 HTML，但不虚构现场 Flow、鉴权方式或定时任务。现场需要保留原路由，并确认 Python 运行环境能访问完整 `m1`、`shared`、`config` 目录。
- Node-RED 版本和第三方节点依赖必须按现场导出清单锁定；本轮不声称已完成真实 Node-RED 导入验收。

## 4. 打包和发布

默认交付方式为本机构建镜像、推送腾讯CCR仓库、生产服务器直接拉取，不要求上传或解压压缩包。HTML/Node-RED Flow若有变更单独同步。以下联合检查包仅为可选离线检查产物，不作为生产更新的默认前置条件。

### 本地生成联合检查包（不推送、不部署）

```bash
.venv/bin/python m4/deploy/build_package.py \
  --include-m1 --platform linux/arm64 \
  --output outputs/m4/releases/product-check
```

输出目录必须不存在。此命令打包当前工作区，用于离线检查；没有镜像引用和提交号的包不是已发布镜像。正式发布按白名单使用已审查的工作区源码，Git基线及内容摘要记录在发布元数据中。

包结构：

```text
backend/                   # M4 Docker/Compose 与运行脚本
  app/m1/                  # --include-m1 时加入，含M1程序与页面
  app/m4/                  # M4正式程序，含运行必需的web/正式HTML
  app/shared/              # 共用配置加载器
  app/config/projects/     # 内置兼容配置与示例
config/project.json        # 实际项目配置的初始模板，升级时保留现场版本
config/example.json        # 新项目配置示例
node_red/                  # Function源码与环境示例；--include-flow才生成M4 Flow
secrets/                   # 仅说明，不附真实凭据
release.json               # 接口/配置版本、镜像、提交、架构、HTML摘要
SHA256SUMS                 # 配套文件校验和
```

联合包不代表一个容器自动托管全部 Node-RED 功能。M1 仍由现有运行入口调用 Python；完整部署封装必须在取得现场 Flow 后验证。

### M4 正式镜像发布

`m4/deploy/build-and-push.sh` 支持 `PLATFORM=linux/amd64` 或 `linux/arm64`。脚本会构建并推送镜像，仅在明确授权发布时执行。

- `m4-<commit>-<architecture>`：提交标签，部署包引用此标签。
- `0.1.0-<architecture>`：可变便利标签，不作为回滚证据。
- 两种架构不共用同一个单架构标签，不覆盖旧 `0.1.0` 标签。
- 脚本仍只发布 M4 镜像；联合 M1 源码包使用前述 `--include-m1` 命令。

ARM64 的打包与脚本参数支持不等于已经在 ARM64 真机验收科学计算依赖。真实构建、HiGHS运行和目标机业务验收必须单独执行并记录。

## 5. 持久化与启动

M4 Compose 显式挂载 `VIFA_PROJECT_CONFIG_HOST` 为 `/etc/vifa/project.json`，并设置 `VIFA_PROJECT_CONFIG`。首次启动缺配置文件时应失败，避免自动创建空目录误启动。

- `M4_INSTANCE_NAME`：Compose 实例名称，默认 `vifa-m4` 兼容已有部署；同主机不同项目必须设置不同值。Compose 原生 `-p` / `COMPOSE_PROJECT_NAME` 如有设置会优先，须保持与目标实例一致。
- `M4_BACKEND_ALIAS`：共享网络上的后端别名，默认 `m4-api`；共用网络的多个项目必须使用不同别名，并让各自 Node-RED 的 `M4_BACKEND_URL` 指向对应别名。不要使用共享网络上重复的服务名 `m4-api` 寻址多个实例。
- `M4_BIND_PORT`：本机访问端口，同主机各项目分别设置。
- `M4_PLATFORM`：与发布镜像架构一致。
- `M4_IMAGE`：使用配套提交镜像。
- `M4_DATA_VOLUME`：当前项目独占的数据卷。
- `M4_SHARED_NETWORK`：实际 Node-RED 共享网络名。
- `M4_AUTO_PLAN_ENABLED=0`：新部署包默认暂停自动任务；配置和数据源核验、旧任务停用后才能显式启用。此项是交付安全默认值，不代表生产已被暂停。
- 继续使用一个 M4 容器、一个 worker。不要未经验证水平扩容。

M4 健康检查先读取本实例 `/m4-api/project` 的站点列表，再读取首个站点的参数存储；不固定站号，不访问上游、不生成计划。

M1 告警库、M4 参数库和完整决策/日计划/滚动历史必须独立持久化，不放入镜像或外部静态目录。升级时保留现场 `config/project.json`、凭据、运行环境配置和数据卷，不能整包覆盖。

备份前暂停写入并确认没有运行任务；SQLite 使用一致性备份或停服务复制，保留完整历史目录。回滚需匹配镜像、Flow、配置和数据版本，不只回退HTML。禁止通过 `docker compose down -v` 更新。

## 6. 兼容性与验收边界

本轮配置契约为 `schema_version=1`，M4 元数据接口交付契约为 `m4-project-v1`。不支持的配置版本应拒绝启动；未来结构变化应新增显式迁移，不静默丢弃字段。

发布验证需区分：配置加载、离线单元测试、真实镜像构建、Node-RED导入、实际数据联通、生产运行。任何一项通过都不能代替后续各项。本轮具体执行证据见项目交接，旧项目全量失败记录不能据此自动视为已解决。
