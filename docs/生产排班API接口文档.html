生产排班 / SCHEDULE API

按「日期 × 部门」提供生产排班日历：哪天上班、哪天休息、哪天放假、哪天停产， 以及当天的计划出勤人数、计划工时与加班工时。供负荷预测等外部系统取数使用。

01接口说明

能取到什么，以及边界在哪

一次请求返回一个日期区间内、每个生产部门每一天的排班情况， 即一张按「日期 × 部门」展开的日历事实表。

返回内容

日历状态当天是上班、休息、法定节假日还是停产
计划出勤在册人数，以及其中排上班 / 休息 / 法定假各多少人
计划工时当天该部门排定的班次时长合计，已扣除休息时段
加班工时加班单的小时数与张数。仅历史日期有值，当天及未来恒为 0

不在范围内

数据粒度边界

数据是排班口径，最细只到「部门 + 班次」， 没有产线、工序、机台维度，也没有产量、工单、节拍。 对接前请先确认这个粒度能否支撑你的模型。

接口只如实返回排班事实，不做任何预测、平滑或插值， 也不对缺失日期补零。相关加工逻辑由调用方自行实现。

覆盖范围

部门编码部门名称在职人数说明
86中山生产一部220主装配与综合车间
113中山智造部142智能制造产线

接口仅返回上表所列部门。如需扩大到其他部门（如仓储、工艺、品质）， 请联系我方开通，开通为配置项调整，不涉及接口变更，调用方无需改代码。

必读

生产环境走 HTTPS。用 http:// 会收到 301 重定向， 部分 HTTP 客户端默认不跟随重定向、且跟随时会丢掉自定义请求头，导致鉴权失败。 请直接用 https://。

04查询排班日历

主接口

GET/api/production/schedule

请求参数

参数类型必填说明
startDatestring必填 起始日期，格式 yyyy-MM-dd，含当天。例：2026-09-19
endDatestring必填 结束日期，格式同上，含当天。与起始日期的跨度默认最多 186 天
deptCodesstring可选 部门编码，多个用英文逗号隔开，例 86,113。 不传或传空＝返回全部已开放的生产部门。 传入白名单之外的编码会被拒绝（见 07 节）

返回结构 · 外层

字段类型说明
codeint200 成功；401 鉴权失败；500 参数错误
msgstring提示信息，失败时是具体原因
data.startDatestring回显本次查询的起始日期
data.endDatestring回显本次查询的结束日期
data.scheduleHorizonEndstring 排班已排到的最后一天（全库口径，与查询区间无关）。超过这一天一律没有数据，返回空 rows 而非报错。排班按月滚动维护，此值会随时间前移，每次请求都应以它为准判断可见边界
data.overtimeDataThroughstring 加班数据的可信截止日，等于服务器当天。这天之后的加班字段都是 0
data.totalint本次返回的行数
data.rowsarray日历明细，按「日期升序 → 部门编码升序」排列

返回结构 · rows 每行

一行代表「某一天 + 某个部门」。9 天 × 2 个部门 = 18 行。

字段类型说明
datestring日期 yyyy-MM-dd
weekdayint星期几，1=周一 … 7=周日
deptCodestring部门编码，如 86
deptNamestring部门名称，如 中山生产一部
statusstring状态码：WORK / REST / HOLIDAY / SHUTDOWN，见 06 节
statusNamestring状态中文名：上班 / 休息 / 法定节假日 / 停产
scheduledHeadcountint在册人数：当天该部门有排班记录的总人数，不论排的是上班还是休息
workHeadcountint其中排上班的人数
restHeadcountint其中排休息的人数，含周末与调休
holidayHeadcountint其中排法定节假日的人数
workRatiodecimal上班人数占比，0~1，四位小数。status 就是按它归类的
plannedHoursdecimal计划工时合计（小时），已扣除休息时段。是计划值，不是实际完工工时
overtimeHoursdecimal加班工时合计（小时）。未来日期恒为 0
overtimeFormsint加班单张数，口径同上
overtimeSettledboolean加班数据是否已成型。false 表示这个数还会继续涨，不代表当天不加班
设计取向

三个人数字段是原始计数，status 只是按阈值归的类。 如果你不认同服务端的阈值划法，可以完全忽略 status， 直接用 workHeadcount / scheduledHeadcount 自行判定，数据是够的。

06状态判定

status 字段是怎么算出来的

源数据只标到人（这个人今天上班、那个人今天休息）， 没有「这个部门今天算不算开工」的现成结论——车间总有值班的人，不是非黑即白。 服务端按上班人数占比归成四档：

WORK上班
上班占比 ≥ 50%
HOLIDAY法定节假日
排法定假的人数过半（优先级最高）
SHUTDOWN停产
上班占比 ≤ 10%，且当天不是周六周日
REST休息
其余情况，含周末大面积休息

判定顺序：先看 HOLIDAY，再看 WORK，再看 SHUTDOWN，都不满足则 REST。 「非周末」那条限制是为了不把正常的周六周日误报成停产。 两条阈值（50% / 10%）可由管理员在线调整，调整后立即生效。

实例走读

2026-09-24（星期四）· 中山生产一部

  在册 220 人
    ├─ 排上班   13 人   → workHeadcount
    └─ 排休息  207 人   → restHeadcount

  上班占比 13 ÷ 220 = 5.9%   → workRatio 0.0591
    ≤ 10%，且 09-24 是周四不是周末
    → status = SHUTDOWN

  计划工时 13 人 × 8 小时 = 104 小时   → plannedHours
翻译成人话：9 月 24 日星期四，生产一部 220 人里只留了 13 个人上班， 计划工时 104 小时，判定为停产。 对照同期的 9 月 19 日星期六——220 人全部上班、计划工时 1760 小时、还加了 1303 小时班， 判定为正常开工。同一个部门，周四停产、周六满负荷，这就是排班数据的价值所在。

07错误码

失败时 HTTP 状态码仍是 200，判断业务码 code

codemsg 示例原因与处理
200查询成功正常返回
401缺少请求头 X-Api-Key 没带鉴权头。检查客户端是否在重定向后丢掉了自定义头
401密钥无效 密钥不对或已被吊销。注意首尾空格、换行符
401接口未配置调用密钥，请联系系统管理员 服务端还没配密钥。这是服务端配置问题，不是你的请求问题，联系管理员
500startDate 不能为空，格式 yyyy-MM-dd 必填参数缺失
500startDate 格式不对，应为 yyyy-MM-dd，当前传入：2026/09/19 日期格式错误，注意是横杠不是斜杠
500endDate 不能早于 startDate 起止日期颠倒
500单次最多查询 186 天，当前跨度 200 天 区间过大，拆成多次请求
500deptCodes 不在可查范围内 传了白名单之外的部门编码。先调 05 节的接口拿可用编码
重试建议

401 与 500 都是确定性错误，重试不会成功， 请勿做自动重试，直接告警。只有网络超时、5xx HTTP 状态码才值得重试。
