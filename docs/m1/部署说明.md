# M1 常驻接口部署

## 范围与实现

M1使用`m1/resident_api.py`常驻API进程，内部监听`127.0.0.1:8811`，Node-RED保留`/dashboard_energy_api`公网入口。不是每次`docker exec`启动一个新Python；模块和私有能源配置只在服务启动时加载。

每次请求使用当前用户凭据并发读取固定场站及电站，再依次读取依赖节点和实时记录。权限与客户拓扑全部校验完成后，并行读取Growatt、两站负载和柜体数据；不缓存完成业务响应，不跨用户复用数据，不改变白名单、时间、功率、告警判定及JSON结构。最多同时处理4个业务请求；无凭据及超容量请求不读取上游。

原`m1/dashboard_energy_api.py` CLI及直接脚本入口保留，默认继续不启用连接池；常驻入口启用每请求独立连接池，用于隔离用户与传输状态。常驻服务不使用内置默认用户Token；能源凭据复用生产私有配置。鉴权失败返回业务提示，不泄露源响应或令牌。

## 文件与隔离

- 镜像：`m1/deploy/Dockerfile`，基底固定已验证的Python3.12生产镜像，覆盖M1源码并替换entrypoint，**不运行基底中的M3/M4服务**。
- 独立Compose：`m1/deploy/compose.yaml`，项目`vifa-m1-api`。使用`M1_API_IMAGE`，不改共享`RUNTIME_IMAGE`、M2独立镜像或M3/PV/M4 Compose。
- `M1_DEPLOYMENT_ROOT`指向实际部署目录；项目及能源配置只读挂载，原`runtime/m1`挂载为`/state`，保留已有告警SQLite，不重建数据库。
- UID/GID10001，host网络、只读根、cap-drop、no-new-privileges和`/dev/mqueue` tmpfs保持。业务端口只绑定loopback，不增加公网端口。
- 配置或能源凭据轮换后需明确重启M1服务；本服务不启动定时采集、预测或设备控制任务。

## 发布步骤

1. 检查实际宿主机、端口8811、当前M1 Flow与启动器、告警数据库权限；记录M2–M4容器ID/启动时间及M4写表开关。
2. 运行`.venv/bin/python scripts/check.py m1`及M1 Node函数回归；使用构建镜像验证就绪、无凭据拒绝、同进程服务与源导入。未经要求不运行浏览器E2E；此版本不修改HTML或CSS。
3. 构建ARM64镜像，经审查后推送并以摘要固定；只启动独立M1服务。先验证`/ready`及认证边界，再切换公网链路。
4. 网关变更由`m1/deploy/node_red_gateway.py`生成，仅改变现行M1的凭据构造、exec/HTTP请求、JSON包装三个节点；保留同一节点ID、页面、路由、用户Token/query兼容及其他节点。
5. 修改前备份生产`flows.json`（0600），断言读取时的整体SHA仍匹配，原子替换并回读；再重载Node-RED。共享Node-RED重载可能让M2分钟采集短暂中断或按已有once配置执行一次；不改其配置，不触发预测或EMS控制。
6. 验证真实公网JSON业务状态与耗时，匿名仍401、当前用户凭据未被默认key替代；复核M2采集追平及M3/PV/M4启动时间不变，`M4_EMS_STATION2_TABLE_WRITES=1`不变。

## 验证边界与回退

`/ready`只说明M1配置和HTTP进程就绪，不代表EMS用户凭据有效或全部数据源成功。内置默认M1凭据已过期，不能把它的失败请求算作正常加载耗时；缺少有效EMS当前用户凭据时，应明确说明成功请求尚未闭环。

回退先恢复此次备份的Flow并重载Node-RED，公网恢复原exec→`m1-launcher.py`链路，再停止独立M1服务。原共享镜像、启动器、私有配置和历史目录不删除、不改动。服务原生响应与健康接口不触发预测或设备动作；正常授权看板请求继续按原逻辑保存告警历史。

发布证据归`outputs/m1/releases/`，测试归`outputs/m1/tests/`。实际镜像、备份位置、耗时及生产验证状态在发布完成后记录，不用历史通过结果代替当前验证。

- EMS场站与电站现已用当次用户Token并行请求；完整权限、启用、归属及拓扑校验仍保留，节点和实时记录仍依赖前一步结果，保持场站错误优先级与有限并发。
