# M3 双电站未来能耗预测设计

日期：2026-08-26  
状态：双电站仓库实现与真实源联调已完成；待现场 NocoBase 结果表、ACL 与外部控制面实施  
详细规范：`docs/superpowers/specs/2026-08-26-m3-two-station-forecast-dashboard-design.md`

2026-08-26 之前的单站三序列合同已废止，不得用于实施、部署或验收。

## 1. 目标与非目标

### 1.1 目标

- 将源系统中的 ES01 和 ES02 视为两个独立电站。
- 每站分别预测 `station_total_load` 和 `storage_soc`，合计四条完全隔离的序列。
- 使用 StatsForecast 生成 15 分钟粒度、未来 24 小时的 96 点预测。
- Worker 主动经 HTTP 拉取数据、运行模型并写入结果表；Dashboard 只读已发布缓存或结果。
- 同一 HTML 同时展示两个电站的实绩、预测、模型状态和七日验收进度。
- 最新快照和连续 7 天验收证据均按完整 `station_id` 隔离。

### 1.2 非目标

- 不计算跨电站总负荷，不引入跨站特征或联合模型。
- 不预测光伏，`solar_power` 不参与负荷计算。
- 不在浏览器运行 StatsForecast、保存凭据或直连原始数据源。
- 不修改 M1/M2，不在本仓库创建或部署 Node-RED/NocoBase 外部工程。
- 不包含 M4 调度决策。

## 2. 电站身份与公开边界

Worker 通过受保护的服务端配置建立两个精确绑定：

| 内部身份规则 | 公开键 | 页面名称 | 序列 |
|---|---|---|---|
| 完整 `es_sn`，后缀为 `ES01` | `station_1` | `1# 电站` | `station_total_load`, `storage_soc` |
| 完整 `es_sn`，后缀为 `ES02` | `station_2` | `2# 电站` | `station_total_load`, `storage_soc` |

- 生产必须配置恰好两个精确完整 ID，不得用后缀自动接纳未知设备。
- 完整 ID 只能存在服务端受保护配置、内部处理和结果表 `station_id` 中。
- 公开 Dashboard API、HTML、浏览器 console 和安全日志只使用公开键与显示名称。
- 两个 binding 必须唯一且按 `station_1`、`station_2` 的顺序配置。

## 3. 原始数据映射和 15 分钟聚合

每条原始记录只属于其 `es_sn` 对应的电站：

```text
station_total_load = 本站 load_power
storage_soc        = 本站 emus_soc
```

`solar_power` 不读取、不相加、不作为模型特征。任何电站都不得用另一站的记录补点或求和。

- 时区固定为 `Asia/Shanghai`，时间桶为左闭右开 15 分钟区间。
- 负荷取本站桶内合格 `load_power` 样本的均值；SOC 取本站桶内最后一个及时、合法的 `emus_soc`。
- 合格桶至少需要 12 个分钟样本，首样本不得晚于桶开始后 2 分钟，末样本不得早于桶结束前 2 分钟。
- 负荷必须 `>= 0`，SOC 必须在 `0..100`。缺失、非有限值、越界或覆盖不足都产生显式 `invalid/null`，不补零。
- 每站使用自己的最新源时间向下取整到 15 分钟得到 `as_of`；一站延迟不改变另一站的窗口。
- 原始实绩不修改。只有训练副本可线性插值连续 1–2 个缺口；长缺口不跨越，插值点不进入验收 MAPE。

## 4. 模型、历史门槛与回退

四条 `(station_id, unique_id)` 序列独立构造训练集、选模、拟合、预测、裁剪和回退。修改任一站输入不得改变另一站的训练数据、冠军或预测。

固定 StatsForecast 候选池：

```text
SeasonalNaive(season_length=96)
AutoETS(season_length=96)
AutoARIMA(season_length=96)
MSTL(season_length=[96, 672], trend_forecaster=AutoARIMA())
```

预测参数固定为 `freq="15min"`、`h=96`。完整选模使用滚动时序交叉验证：`h=96`、`step_size=96`、`n_windows=7`，禁止随机切分和未来泄漏。

| 每序列有效历史 | 行为 |
|---|---|
| 少于 7 天 | `insufficient_history`，发布空预测点集，不伪造数据 |
| 7 天至不足 28 天 | `SeasonalNaive(96)`，状态 `warming_up` |
| 至少 28 天 | 运行候选池交叉验证并选择本序列冠军 |

- 冠军预测失败时，只对当前序列回退到 `SeasonalNaive(96)`并标记 `degraded`。
- 冠军与基线均失败时，当前序列返回安全 `error/forecast_failed` 与空点集，不得暴露原始异常。
- 负荷发布值裁剪到 `>=0`，SOC 裁剪到 `0..100`，同时保留 `raw_forecast` 和 `is_clipped`。
- 一条序列失败只使本站快照降级；健康序列和另一站仍可独立发布。

## 5. Worker 主动流程与 HTTP 边界

```text
固定原始源 HTTP API
  → 按精确 station_id 分页拉取
  → 本站 15 分钟聚合与 90 天内存缓存
  → 每序列 StatsForecast 预测
  → 按 station_id 经 NocoBase HTTP API 发布
  → Dashboard 只读缓存/结果表
```

- Worker 启动时及每日选模前主动拉取最近 90 天历史；在线期间主动增量刷新并吸收迟到修订。
- 浏览器、Dashboard GET 和 Node-RED 不触发训练或预测。
- 生产 Worker 只允许一个调度器实例；每站任务与模型选择使用独立互斥边界。
- 原始源、运行告警客户端与 NocoBase 使用三组职责分离的固定 URL/凭据；NocoBase 是唯一验收任务控制源，入站参数不得改写出站目标。
- HTTP 客户端拒绝重定向，设置超时、连接池、响应体、页数和窗口上限；只对允许的网络/HTTP 错误做有界重试。
- Worker 只通过 NocoBase Resource API 读写，不直连 PostgreSQL。

## 6. 最新快照与七日验收

四个逻辑结果/明细集合保持不变：

- `energy_forecast_latest`：每个完整 `station_id` 一行最新快照，按站 upsert；同站两序列达到明确终态后原子发布。
- `energy_forecast_batches`：每站每日一个不可变基线批次，使用 `writing → complete` 可恢复发布协议。
- `energy_forecast_points`：保存不可变预测字段，实绩到达后只允许回填明确列。
- `energy_forecast_evaluations`：每站保存两条序列结果及 `overall` 结论。

第五个集合 `energy_forecast_acceptance_runs` 是验收的控制/汇总表，不重复 metrics；详细证据仍保留在 batches、points、evaluations。操作员创建并拥有任务身份、窗口和控制字段；Worker 列出任务行，且只能更新 `completed_days`、`result_state` 和 `calculated_at` 三个汇总字段。

自定义预测不复用上述固定 15 分钟合同，新增三个独立集合：

- `energy_forecast_manual_runs`：保存场站、历史窗口、预测窗口、输出粒度、模型策略、执行状态和内容哈希；`station_id + idempotency_key` 防止重复提交。
- `energy_forecast_manual_points`：按任务、序列和目标时间保存不可变预测值，并在实绩可用后只更新实绩与误差字段。
- `energy_forecast_manual_evaluations`：保存两条序列及 overall 摘要；近七日指标只聚合同场站、同序列、同粒度、同预测天数、同模型策略的数据。

30 秒、7 天时每条序列最多 20,160 点，两条序列共 40,320 点，因此点表使用 `integer` horizon、
索引覆盖的 `bigint` 外键和 `(run_pk, unique_id, target_time)` 唯一约束。任务、点和评估均禁止
Worker 删除；现有自动预测、正式验收及其计数不变量保持不变。

当前计数不变量：

| 范围 | 理论点数 |
|---|---:|
| 单站单日基线 | 2 序列 × 96 = 192 |
| 单站单序列七日 | 7 × 96 = 672 |
| 单站两序列七日整体 | 2 × 672 = 1,344 |

- 正式基线每日固定一批，连续保存 7 天；普通滚动预测只覆盖最新快照。
- 两站批次、点位、实绩回填、评估和结论均按 `station_id` 隔离。
- 每条序列独立计算标准 MAPE；`actual=0` 单独计数，不修改分母。至少 605 个合格非零点才可判定，否则为 `insufficient_data`。
- 两条序列均满足覆盖率且 `MAPE <= 30%` 才可判定单站通过；不跨站、不跨序列平均掩盖失败。
- 终态任务摘要只从同站同任务的 `station_total_load`、`storage_soc`、`overall` 三行完整评估恢复；三个键、窗口、计算时间和组合结果必须严格一致。
- 启动按站依次恢复 `writing` 批次和任务摘要；某站失败只告警该站，其他站继续，但任一失败都会使 readiness 保持 `false`。
- 每个任务摘要写边界要求 `control_state=active`。固定 NocoBase 更新接口没有控制状态 CAS，因此取消会阻止后续调度并在请求前再次检查；只有已经发出的摘要请求可能与取消并发完成，且不能修改 `control_state`。

本地联调 Dashboard 另行计算不落库的历史滚动回测：以最近一个完整自然日边界为终点，设置 7 个逐日预测起点；每条序列仅使用七日窗口开始前的历史选择一次固定冠军，随后每个起点只使用此前历史重新拟合该冠军并预测 96 点，既避免选模窥视留出期，也避免逐窗口重复遍历候选池。同一电站同一自然日只计算一次，结果写入本站公开 `acceptance` 缓存字段。该回测展示 MAPE、MAE、SMAPE、WAPE、中位 APE 和 P90 APE；当前没有停机、检修、SOC 策略切换或传感器异常日期清单，因此不做业务事件剔除，所有质量为 `valid` 且能与预测对齐的实绩均参与评分。

## 7. Dashboard 公开合同

浏览器只调用同源固定路径：

```text
GET /energy-forecast-api
```

成功响应使用 `data.stations[]` 嵌套拓扑：

- `stations` 恰好两项，顺序为 `station_1`、`station_2`。
- 每站 `series` 恰好两项，顺序为 `station_total_load`、`storage_soc`。
- 每站有自己的 `range`、`system`、`series` 和 `acceptance`；两站可以有不同 `as_of`、预测窗口和模型状态。
- 本地联调时 `acceptance` 承载后台每日缓存的七日历史滚动回测；浏览器只负责严格校验和渲染，不新增回测 GET，也不在请求处理中训练模型。
- 顶层 `system` 只汇总整体严重性、生成时间和健康电站数，不混合业务序列。
- 每条可预测序列有最多 96 个过去实绩点与恰好 96 个未来点；历史不足/错误序列使用明确状态和空预测集。
- HTML 固定展示两个电站分区、四张指标卡、四张 48 小时图和两个站内验收区。
- 实绩用实线，预测用虚线；缺失点断线，不补零。窄屏页面不得产生页面级横向溢出。
- 首次加载立即 GET，之后每 60 秒在页面可见且无 in-flight 请求时刷新。GET 只读缓存，不运行模型。
- HTML 与嵌套 API 合同必须作为一个发布单元同步部署。

## 8. 失败、陈旧与恢复

- 原始源整体不可用：保留两站各自的最后有效结果；超过 30 分钟后独立标记 `stale`。
- 单站无数据、合同错误或刷新失败：只将该站标记 `error/degraded/stale`，另一站继续发布。
- 单序列历史不足或预测失败：只影响该序列，同站另一序列和对站不受影响。
- 从未成功的站使用严格空拓扑，不生成演示值；已有成功结果的站在后续失败时保留本站最后有效结果。
- 快照只在完整经过明确 DTO 验证后原子替换；部分结果不对浏览器可见。
- 验收批次用持久化的原始点模板从 `writing` 恢复，不重跑模型替换已生成基线。

## 9. 安全边界

- 原始源 bearer、运行告警客户端 bearer、NocoBase API Key 和 Worker 入站管理 token 分离配置，以 `SecretStr`/等效语义遮蔽。
- 凭据只从环境或受保护密钥文件读取，不进入 URL、HTML、API 响应、日志、工单或截图。
- 公开响应不定义完整内部身份字段，并在 DTO 转换后递归扫描内部身份泄漏。
- 出站 URL 是受控配置，浏览器和 Worker 入站参数不得修改 URL、collection、action 或凭据。
- 生产 Worker 只绑定回环、受控容器网络或经认证的内部网络；跨主机 HTTP 必须升级为 HTTPS 并验证证书。
- NocoBase Worker 只使用一个专用 `M3_NOCOBASE_API_KEY`；其单一角色合并四个 M3 结果/明细集合既有权限、批次/评估限定读取及 `energy_forecast_acceptance_runs` 汇总更新，不另配验收任务 Key，也不得拥有删除、全库、管理员或数据库直连权限。
- Dashboard 只读账号由现有 EMS 认证上下文派生允许站点，必须用跨租户负例证明拒绝越权读取。

## 10. 运行、可观测性与上线门槛

每次任务只记录公开站点键或受控的内部调度身份、任务类型、安全时间窗口、输入/有效/插值/裁剪点数、模型名、状态、耗时、HTTP 状态和安全错误码。不记录 token、请求头、完整查询参数或原始响应正文。

关键告警包括：启动恢复失败、源拉取失败、最新快照写入失败、预测连续失败、超过 30 分钟未成功发布、每日选模失败、正式基线缺失和验收覆盖率不可达。

上线前必须同时满足：

1. 完整 M3 Python、HTTP/JSON、持久化合同和 Dashboard 浏览器回归通过。
2. 真实源证明两个电站精确绑定、负荷/SOC 字段映射、跨站隔离和公开身份脱敏。
3. NocoBase 四个结果/明细集合和 `energy_forecast_acceptance_runs` 的约束、relation/index、已安装版本 API 契约、Worker 最小权限和 Dashboard 跨租户 ACL 由 operator 实施并签字。
4. HTML 与当前嵌套双站 API 同步发布，浏览器无凭据/完整身份泄漏，390px 无页面级横向溢出。
5. M1/M2 不在 M3 变更范围内；用户在 `vifa/m2/**` 的并发变更不得由 M3 任务修改或回滚。

## 12. 连续七日验收生产启用

示例任务字段（不是生产 ID）：

```text
station_id:          ES01-FULL-ID-EXAMPLE
acceptance_run_id:   acceptance-20260829-station1
window_start:        2026-08-29T01:00:00+08:00
window_end:          2026-09-05T01:00:00+08:00
control_state:       active
completed_days:      0
result_state:        pending
calculated_at:       留空
```

日期仅为示例。每个真实任务从上海时间 01:00 开始，恰好七天后结束，且在首日 01:02 调度槽之前创建。安全模板和默认值为 `M3_ACCEPTANCE_ENABLED=false`；只有新镜像已部署、活动任务已创建且任务表探针成功后，生产才将其改为 `true`。

以下探针用同一个 Worker Key 覆盖任务、完整批次、`writing` 恢复批次和评估的固定读取合同。Authorization 头从 stdin 传给 curl，不出现在 curl argv。不得用生产记录测试写入；在 NocoBase 角色 UI 中核验同一 Key 只有：latest `list/updateOrCreate`、batches `list/update/firstOrCreate`、points `list/update/firstOrCreate`、evaluations `list/updateOrCreate`、acceptance runs `list/update`，并逐项核对机器合同中的字段/过滤/排序/写入/记录键。

```bash
read -rsp 'Worker NocoBase token: ' M3_PROBE_TOKEN
echo
read -rp 'Full station ID: ' M3_STATION_ID
read -rp 'Acceptance run ID: ' M3_ACCEPTANCE_RUN_ID
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_acceptance_runs:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"control_state\":\"active\"}" \
  --data-urlencode 'fields=id,station_id,acceptance_run_id,window_start,window_end,control_state,completed_days,result_state,calculated_at' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_batches:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"acceptance_run_id\":\"${M3_ACCEPTANCE_RUN_ID}\",\"write_state\":\"complete\"}" \
  --data-urlencode 'fields=station_id,acceptance_run_id,issued_at,forecast_start_time,forecast_end_time,write_state' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_batches:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"write_state\":\"writing\"}" \
  --data-urlencode 'fields=id,station_id,acceptance_run_id,issued_at,forecast_start_time,forecast_end_time,status,write_state,model_manifest,content_hash,point_templates' \
  --data-urlencode 'sort=issued_at' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
printf 'Authorization: Bearer %s\n' "${M3_PROBE_TOKEN}" | curl --fail --silent --show-error \
  --header @- \
  --get 'https://vifa.hlszh.com/api/energy_forecast_evaluations:list' \
  --data-urlencode "filter={\"station_id\":\"${M3_STATION_ID}\",\"acceptance_run_id\":\"${M3_ACCEPTANCE_RUN_ID}\"}" \
  --data-urlencode 'fields=station_id,acceptance_run_id,evaluation_key,window_start,window_end,outcome,calculated_at' \
  --data-urlencode 'page=1' \
  --data-urlencode 'pageSize=1000'
unset M3_PROBE_TOKEN M3_STATION_ID M3_ACCEPTANCE_RUN_ID
```

生产启用顺序固定为：

1. 核验表约束和 Worker 角色权限。
2. 在 `M3_ACCEPTANCE_ENABLED=false` 下部署新镜像。
3. 为每个需要启用的电站创建一个活动任务。
4. 核验每个活动/空电站查询。
5. 在 `/etc/vifa-m3/m3.env` 中设置 `M3_ACCEPTANCE_ENABLED=true`。
6. 在首个 01:02 槽之前只重建 `vifa-m3-worker`。
7. 在 01:02 后检查首个完整 batch 和任务汇总。
8. 在最终实绩回填和评估完成前保持 `control_state=active`。
9. 仅在 Dashboard 显示终态 7/7 结果后将任务标记为 `completed`。

`m3_production_gateway_flow.json` 不需要为本变更重新导入；生产 Node-RED 保持不变。
