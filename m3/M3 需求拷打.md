# M3 未来能耗预测：Grill / Discovery Notes
Date: 2026-08-25 · Goal: 从项目负责人视角穷尽 M3 的产品范围、数据口径、StatsForecast 模型策略、评估验收、运行架构、界面与交付风险，为后续设计和实现形成可靠输入。

## Summary / key decisions

- M3 严格按验收文档收敛，只实现负载用电需求预测和储能 SOC 趋势预测，不实现光伏发电功率预测。
- 负载预测对象为厂区总负荷，不预测各用电支路；SOC 按每套独立储能系统分别预测，不计算场站汇总 SOC。
- 当前第一阶段至少形成三条预测序列：`station_total_load`、`storage_1_soc`、`storage_2_soc`。
- 30 秒级原始数据按 15 分钟左闭右开时间桶转换；时间戳记录桶起点。总负荷取桶内有效功率的时间加权平均值，SOC 取桶结束前最后一个有效值，缺失数据不补零。
- 负荷时间桶需至少覆盖 12 分钟且相邻有效样本间隔不超过 120 秒；SOC 样本距桶结束不得超过 90 秒。未达标桶标记为 `invalid`，不产生伪造实绩且不参与验收 MAPE。
- 原始实绩和验收数据永不插值；仅 StatsForecast 训练副本允许对最多连续 2 个缺失桶（30 分钟）线性插值，并标记 `is_imputed=true`。更长缺口不跨越插值。
- 正式模型使用最近 90 天历史，至少积累 28 天后运行完整候选模型与交叉验证。7–27 天使用 `SeasonalNaive(96)` 冷启动并标记 `warming_up`；少于 7 天返回 `insufficient_history`。各预测序列独立降级。
- M3 首版为单变量预测，仅使用历史总负荷和各储能历史 SOC；天气、电价、节假日和生产班次等外生变量不进入本次范围。
- 三条预测序列使用同一 StatsForecast 候选池并独立选型：`SeasonalNaive(96)`、`AutoETS(96)`、`AutoARIMA(96)`、`MSTL([96, 672], trend_forecaster=AutoARIMA())`。
- 模型选型采用滚动时序交叉验证：`h=96`、`step_size=96`、`n_windows=7`，对应连续 7 个历史预测日；插值点和无效实绩不评分，禁止随机切分和未来数据泄漏。
- 验收使用标准 MAPE，不通过 epsilon 修改分母。`actual=0` 的点排除出 MAPE 但记录 `zero_actual_count`；MAE、SMAPE 仅作补充诊断，有效非零实绩不足时不得宣称通过。
- 七日验收中，每条序列至少需要 605/672 个非零、非插值、质量合格实绩点。总负荷、1# SOC、2# SOC 分别计算且都须 MAPE≤30%；任一序列数据不足则结论为“数据不足”，不做通过/不通过判断，也不以跨序列平均掩盖问题。
- 保存 StatsForecast 原始预测；对外负荷预测下限为 0，SOC 限制在 0–100%，预测区间同样裁剪。修正点标记 `is_clipped=true`；MAPE 按对外交付的边界修正后预测计算。
- 每个 15 分钟桶结束 2 分钟后生成新一版未来 24 小时预测；每天 00:30 对四个候选模型重新做七窗口交叉验证并分别选择冠军。在线预测仅用当前冠军和最新历史重新拟合，调度时区为 Asia/Shanghai。
- 冠军预测失败时在 StatsForecast 内降级到 `SeasonalNaive(96)` 并标记 `degraded`；仍失败则保留最后成功结果。成功结果超过 30 分钟未更新标记 `stale` 并告警。每日模型重选失败时沿用上一冠军，不生成模拟预测。
- 正式验收每天固定使用 01:02 生成的不可变基准批次，覆盖 01:15 至次日 01:00 的 96 点；连续 7 批构成 672 点。其他 15 分钟滚动预测不混入验收，基准批次不可事后改写或挑选。
- 部署采用 Node-RED Source API + 同机常驻 Python Worker：Worker 内置单实例调度器，主动通过 HTTP 拉取 Node-RED 已归一化的数据、运行 StatsForecast，并通过 NocoBase HTTP API 写结果表；Node-RED 不再触发或推送预测任务，生产不使用 exec 节点反复启动 Python。
- 当前阶段持久化两类结果：每场站一行、每 15 分钟 HTTP upsert 覆盖的最新预测快照，以及七日验收证据。每天 01:02 保存一个三序列、每序列 96 点的不可变基准批次，七天共 2016 点；普通滚动预测不保存历史版本。
- Worker 启动或每日选型前主动分段拉取最近 90 天标准长表历史，之后每 15 分钟主动拉取最新桶和重叠修订窗口；Worker 仅在内存维护训练缓存，重启后自动重拉。目标时间过去后 Worker 再主动拉取实绩，并通过 HTTP 回填七日验收记录。
- M3 使用独立 `场站未来能耗预测.html` 和同源 `GET /energy-forecast-api`，通过单独 iframe/菜单嵌入 NocoBase；现有 M1/M2 能流页面保持不变，并延续受限的 iframe token 透传规则。
- 页面采用两张 48 小时图：总负荷单图，以及 1#/2# SOC 双线图；均展示过去 24 小时实绩和未来 24 小时预测。实绩实线、预测虚线、当前时刻分界；缺失点断线。首版仅展示点预测，不加入置信区间。

## Source baseline

- 验收文档将 M3 定义为“未来能耗预测”，包含：能耗预测算法模型部署、负载用电需求预测、储能 SOC 趋势预测，以及连续 7 天 MAPE 不大于 30%。
- 已确认负载预测与 SOC 趋势预测全部采用 StatsForecast，不引入 MLForecast、NeuralForecast 或其他预测模型库。
- 已确认预测口径为未来 24 小时、每 15 分钟一个预测点，即每次输出 96 个点。
- 当前仓库 `m2/` 已有 M1/M2 的纯 Python 计算模块、分钟历史与瓶颈逻辑、测试和 iframe 看板；真实 NocoBase API、字段映射和 HTTP 适配层仍待真实接口确定。
- 第一阶段设备范围包括 1#、2#配电站及储能、两组原有光伏、市电及关口计量、厂区总负载和双方确认的用电支路。

## Q&A log

### Q1 — 预测目标范围
- Asked: M3 是否除负载预测和 SOC 趋势预测外，同时实现光伏发电功率预测？推荐实现三类预测，以便为 M4 提供光伏输入。
- Captured: 用户原话：“不需要，根据文档收敛。”据此，M3 只包含验收文档明确要求的负载预测与储能 SOC 趋势预测；光伏预测不纳入本次范围。
- Flags: 无。

### Q2 — 预测对象层级
- Asked: 是否采用“厂区总负荷一条序列、每套独立储能系统各一条 SOC 序列”，不预测用电支路、不计算场站汇总 SOC？
- Captured: 用户原话：“确认”。据此，负载仅预测厂区总负荷；1#、2#配电站储能 SOC 分别预测，不能按不同容量和运行状态直接平均。
- Flags: 真实设备唯一标识和最终 `unique_id` 映射仍需电子点表或接口样例确认 -> 数据接口负责人。

### Q3 — 15 分钟训练点的聚合口径
- Asked: 是否采用 15 分钟左闭右开时间桶，总负荷取有效功率的时间加权平均值，SOC 取桶结束前最后一个有效值，并且不把缺失数据补零？
- Captured: 用户原话：“确认”。据此，StatsForecast 的 `ds` 使用时间桶起点；负荷目标单位为 kW，SOC 目标单位为百分比。
- Flags: 已由 Q4 解决。

### Q4 — 15 分钟桶的有效性标准
- Asked: 是否采用“负荷覆盖不少于 80% 且最大样本间隔不超过 120 秒；SOC 末值距桶结束不超过 90 秒；无效桶不参与 MAPE”的标准？
- Captured: 用户原话：“确认”。据此，负荷桶至少覆盖 12 分钟；不合格桶保存 `invalid` 状态，但不生成可用于验收的实际值。
- Flags: 已由 Q5 解决。

### Q5 — 训练序列的短缺口处理
- Asked: 是否允许只在模型训练副本中对最多连续 2 个缺失桶进行线性插值，同时保持实绩和 MAPE 数据完全不插值？
- Captured: 用户原话：“确认”。据此，插值点必须可追溯；连续缺失超过 30 分钟时不跨越缺口，训练只能使用缺口之后满足要求的连续数据。
- Flags: 已由 Q6 解决。

### Q6 — 历史窗口与冷启动
- Asked: 是否采用最近 90 天训练、28 天后启用完整模型选型、7–27 天使用 `SeasonalNaive(96)`、少于 7 天不预测，并让各序列独立降级？
- Captured: 用户原话：“确认”。据此，冷启动输出必须带 `warming_up` 状态且不作为正式验收模型；单条 SOC 序列历史不足不阻断其他序列。
- Flags: 无。

### Q7 — 外生变量范围
- Asked: 按文档收敛，M3 首版是否只使用历史目标序列，不接入天气、电价、节假日或生产班次等外生变量？
- Captured: 用户原话：“确认”。据此，日内和周内规律由 StatsForecast 季节模型从历史序列学习；外生变量仅作为后续调优方向，不构成本次依赖或验收项。
- Flags: 无。

### Q8 — StatsForecast 候选模型池
- Asked: 是否让总负荷和两套 SOC 共用四模型候选池，并由每条序列独立选出冠军模型？
- Captured: 用户原话：“确认”。候选池固定为日周期 SeasonalNaive、日季节 AutoETS、日季节 AutoARIMA，以及日/周双季节 MSTL；简单基线始终保留用于对照。
- Flags: 具体 StatsForecast 版本锁定和模型构造参数需要在实现设计中固化并通过回归测试验证 -> 开发负责人。

### Q9 — 交叉验证方式
- Asked: 是否使用 `h=96`、`step_size=96`、`n_windows=7` 的滚动时序交叉验证，并按最多 672 个历史预测点的综合 MAPE 选择模型？
- Captured: 用户原话：“确认”。据此，每个验证窗口预测完整未来 24 小时，每日滚动一次；插值点与无效实绩排除在评分外。

### Q10 — MAPE 零分母

### Q25 — 主动 HTTP 拉取与写表
- Asked: 是否修改部署方式，让模型侧主动请求数据并通过 HTTP 把结果写入表？
- Captured: 用户原话：“部署方式我想修改一下，由模型发起请求数据，且将结果写到表中。都是通过http的方式”。据此，“模型侧”实现为常驻 Python Worker 的调度/应用层：Worker 主动调用 Node-RED 只读 Source API 获取已归一化数据，StatsForecast 保持纯计算；Worker 再调用 NocoBase Resource API 写入每场站最新预测快照和七日验收表。Node-RED 不再向 Worker 推送 bootstrap/增量，也不再触发自动预测任务。
- Flags: Source API、生产 NocoBase 基础 URL、API Key 角色和当前部署的 `updateOrCreate/firstOrCreate` 请求格式由接入阶段核对；不阻塞逻辑设计。
